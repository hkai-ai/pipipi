# 已批准图片转印花模板

以下嵌入完整方法正本与作者合同。当前任务只产候选，不生成图片、不修改已批准图片、不入库、不发布。
无 Tool 环境：不执行文档内脚本、文件、网络、后台、导入或生成操作；像素测量仅使用宿主本次提供的证据，未测量的统计不得编造。
流程版本 v3 与运行语义 v4 分别管理。只输出 inputSchema.version=2 与 runtimeSemantics.version=4；没有 visualContract、promptEnhancement 或 preprocessSteps。本文后半的 v1～v3 示例仅为版本兼容背景，不能用于本次输出。
先看真实附件，记录整体、文字、颜色、层次和印花风险，再编写 designSpec。默认 same_design；输入绑定只开放当前引擎能消费的主体照片（全模板最多一个且 maxCount=1）及文本、配色。其他元素只开放文字；不创建内容图片或 reference_only 输入。
将原物与外形词留在 instance/originalObject/shapeFeatures 作为证据，defaults 写可执行的作者默认迁移；不得为通过检查伪造原始观察，执行描述不得混入原物外形。可替换默认答案不写入 technique、purpose、layout.role 或固定关系。描述可用 @元素id 与 {色:角色名} 引用。版面框为候选，必须人审叠图核对。
每个文字元素都有 defaults.texts，随主体的名字/释义标 followsSubject；固定口号保持默认字。配色角色有默认颜色。所有开放槽的文字默认值必须与绑定目标的 defaults 一致；主体可以 text+image，文字与配色只用 text。promptTemplate 由服务端从 defaults 单向生成，模型不得维护第二份提示词。
印花形态按已批准图片选一个：完整图形 standalone；场景/海报 rect_patch 且要有真实设计边框的 edge 元素；切开主体 bleed_crop。不能凭空声称审批图已有边框或已适合印刷；有缺陷如实标 needs_prep/not_for_apparel 并在观察中说明，运营可退回图片步骤重做。表达机制是推断，保留给人工确认。
首次输出 {observation,draft}，draft 只包含 key/title/description/inputSchema/runtimeSemantics/metadata(tags)。独立复核重新看同一批准图，只修有依据的字段并给出检查报告，不增加图片生成或自动采用。

# 印花设计预处理与验收框架

更新日期：2026-11-04。

适用范围：从题材、参考图或 IP 形象出发，准备面向 POD 的新印花设计。构思、拆解参考、把参考图结构化并据此反推新图、编写生成任务书与评估结果时阅读。

本文记录当前讨论形成的设计方法、参考样本观察与待验证事项，不代表系统已实现这些步骤，也不替代模板运行、商品印区或生产交付合同。这里只讨论创作准备，不定义 API、数据结构或模型执行管线。

## 核心判断

六层设计既用于拆解参考图，也用于决定本次方案保留什么、改变什么。目标是把图拆成结构化数据，再用这份数据生成同类新图，而不是还原原图。Layout 是推导结果，不是按题材预先绑定的固定答案。

- 借鉴参考要保留的是“神”，不是“形”。先确定保留手法、意境还是身份，再决定哪些形可以改变；不要求逐像素还原。
- 好看 = 底线 + 手法。意境不是每张 POD 印花的必选项，装饰款以好看为目标即可。
- 参考图的既有做法不自动成为美学标准；先分析，再判断是否值得继承。
- 专业术语、关系说明与具体描述可以叠加：术语明确方法，关系解释作用，细节帮助执行。
- 可复用约束描述角色、主次与关系；某次设计的坐标、分格数量和摆放位置属于具体方案。
- 锁关系，不锁实例：疏密锁元素之间的关系，不锁画布边距；颜色锁色彩关系，不锁色值；字体锁字层对比与气质，字形随主体推出。
- 白底插画好看，不等于适合穿在衣服上；角色相似，也不等于表达与构图成立。
- 六层是分析与检查维度，不是不可回退的流水线。商品印区等已知条件应尽早进入构思，不能等画完再适配。

## 保留什么：手法、意境与身份

| 保留对象 | 常见用途         | 不变量                                                 | 可变项                                   |
| -------- | ---------------- | ------------------------------------------------------ | ---------------------------------------- |
| 手法     | 装饰款，POD 主体 | 外轮廓、配色关系与色数、线条语言、构成方式、字层、质感 | 题材与内容                               |
| 意境     | 叙事或情绪款     | 情绪，以及承载情绪的少数关系                           | 构图、动作、场景与具体元素               |
| 身份     | IP 款            | 影响识别的外观特征                                     | 动作、视角、场景；服装按该 IP 的要求判断 |

三者可以组合，每次在任务书中写明本次保留哪一种或哪几种。底线对所有类型都适用。

### 手法：形就是被保留的对象

手法款中，轮廓、配色、线条和构成这些“形”的特征正是要保留的东西，可替换的是题材。例如同一种复古徽章手法可以承载猫、咖啡杯或快递员。验收时问：新图与参考是否像同一设计师做的同一系列。

### 意境：保留承重关系

意境由少数承重关系支撑。“夜班快递员”的“深夜独行的安静”依靠人物小于环境、大面积暗部、单一光源、舒缓动作和画面中没有其他人。换成雨夜骑行、只有一块霓虹招牌，形完全改变，意境仍在；反之人物放大提亮，内容正确也会削弱意境。

判断承重关系时，逐项设想去掉或改变某个元素：去掉路灯还安静吗？人物放大还安静吗？意境随之崩塌的才是承重关系。模型可以提出候选，由人确认。

意境词须具体并给出对照，例如“安静，不是孤独，也不是疲惫”；每个词指向画面依据，避免“温馨、治愈、有氛围感”等套话。

### 标志特征与复刻刻度

标志特征是让人一眼认出某张参考图的 1～3 个能指，例如 TROUT 的条纹填充主标、青绿加薰衣草紫的文字配色、主体压住主标下部。普通用户判断“像不像”主要看这类表面特征；手法的深层关系（叠层、字层对比、色彩关系、气质）设计上更重要，却不一定被认出。

借鉴参考因此不是二选一，而是一个刻度：

| 档位     | 锁定                                         | 放开                                       | 适合的意图                   |
| -------- | -------------------------------------------- | ------------------------------------------ | ---------------------------- |
| 同款     | 标志特征与大部分表面特征（字体、字效、配色） | 题材与文字；必要时重建机制                 | “我要这个效果，换成我的东西” |
| 标志特征 | 标志特征与手法关系                           | 其余字体维度、主体配色与文字元素从题材推出 | 既要认得出，又要贴合题材     |
| 同手法   | 手法关系（结构、字层对比、色彩关系、气质）   | 标志特征与全部表面特征                     | “给我的题材做一个同样好看的” |

标志特征须在结构化时单独标出；它与“系列感”是同一件事：要更强的系列感，就多锁标志特征。

用户在“做同款”时想要哪一档尚未验证。验证方式：同一组参考与各档结果，分别问“哪张是这张的同款”（认出）与“哪张更愿意买”（偏好），两题答案的差距决定默认档位与是否提供切换。

### 底线

所有 POD 印花都应满足，无需从参考图提取：

- 外轮廓完整，在衣身上能作为一个整体形状被读出；
- 远看有明确焦点和层级；
- 色数克制，配色在目标底色上协调；
- 没有无意图的拥挤、截断，或缩小后不可辨的碎细节。

## 六层设计

六层设计描述一张图：它画了什么、表达什么、通过什么机制成立，以及如何组织、呈现和落到商品上。拆解参考图时逐层记录观察；准备新方案时逐层标记本次的不变量与可变项；验收时逐层检查结果。它不是六步生成流程，也不是统一行业标准。

| 层次        | 核心问题                         | 记录内容                                                                 | 避免混淆                                                   |
| ----------- | -------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| 1. 内容题材 | 画面中有什么？                   | 主体、身份、动作、场景、道具、准确文字及其语义                           | “咖啡”是题材，不是画风或布局                               |
| 2. 表达意图 | 希望观者感受到或认同什么？       | 幽默、态度、情绪、身份认同，或单纯的装饰趣味                             | 不强行为装饰款补故事；参考图意图属于推断，需与可见事实分开 |
| 3. 表达机制 | 内容通过什么关系产生意义或趣味？ | 语言双关、拟人、反差、并置比较、图文互释、同主题聚合等                   | 机制解释“为什么成立”，不等于元素位置或风格名称             |
| 4. 视觉组织 | 元素在空间中如何关联、引导观看？ | 图文关系、层级、尺度关系、排列、遮挡、嵌合、重复、内部疏密、外轮廓和负形 | “居中”不足以说明组织；画布边距不属于设计                   |
| 5. 视觉语言 | 这些内容以什么形式被画出？       | 线条、色彩关系、明暗、造型、字体、材质与纹理的共同特征                   | 同一布局可以有不同画风；“复古”“手绘”还需具体特征支撑       |
| 6. 印花适配 | 放到目标商品后是否仍成立？       | 印区与外轮廓比例、实际尺度、衣身底色、细节可读性与工艺条件               | 插画效果不等于穿着效果；缺少商品或工艺信息时保留待验证状态 |

美学是横跨各层的判断，不是给六层增加一个泛泛的“好看”标签；其中注意力、重量、节奏与空间的安排主要落在视觉组织。

六层之上另记一项**整体调性**：一句话说明这张图整体是什么味道（年代、气质、情绪），作为各层的总纲。只拆零件而不记整体时，各层分别正确，合起来仍可能不是原来的味道。调性用风格名称描述时会带入相关内容，须注明“只借调性，不加入相关元素”。

### 能指与所指：锁定方案

六层可以按能指（用什么形式说）与所指（说的是什么）分组：

| 分组           | 层次               | 说明                                                               |
| -------------- | ------------------ | ------------------------------------------------------------------ |
| 所指           | 表达意图、表达机制 | 图要传达的意义、态度或趣味，以及它为什么成立                       |
| 跨两侧         | 内容题材           | 狗、咖啡杯是可见的能指；“职业”“日常”等语义属于所指                 |
| 能指           | 视觉组织、视觉语言 | 元素如何组织、以什么形式画出                                       |
| 能指的物质条件 | 印花适配           | 能指落到商品上的尺度、底色与工艺；由商品条件决定，不随保留对象变化 |

能指与所指之间没有固定绑定：同一所指可以换不同能指表达，同一能指也可以承载不同所指。保留对象因此就是锁定方案，决定本次锁哪一侧、放开哪一侧：

| 保留对象 | 锁定（不变量）                           | 放开（可变项）                                 |
| -------- | ---------------------------------------- | ---------------------------------------------- |
| 意境     | 所指：表达意图，以及承载它的少数承重关系 | 其余能指：构图、动作、场景与视觉语言           |
| 手法     | 能指：视觉组织与视觉语言                 | 题材与所指；依靠机制的设计须在新题材中重建机制 |
| 身份     | 内容题材中的识别特征及其造型             | 动作、视角、场景与其余能指                     |

所指不只在整张图的层面，每个元素也有自己的所指，即它在图里起的作用，例如“主体所在的世界”“与主体互相解释的口号”。只记录元素的外形而不记录作用时，可调的只剩“给模型多少外形”这一个量：给多了照抄原图，给少了由模型默认值填充，两头都会失败。记录作用之后，换题材时可以锁住作用与关系，由新题材重新推出外形。整体调性中的风格名称（如“七十年代迷幻”）指向一套视觉素材，不是所指。

“要意不要形”即锁所指、放能指；手法款方向相反。三者可以组合，组合后逐层标记不变量与可变项。依靠语言双关等机制成立的设计，锁定的是机制本身；换题材时用新的能指重建同一机制，而不是保留原词替换图像。

### 记录方式

每层采用“专业术语 + 关系说明 + 可见依据”的描述；记录参考图时，将观察、意图推断、继承决策和未验证项区分开。几何量的获取与可靠性遵循下文“结构化与反推”，不让语言描述代替测量。

例如视觉组织可以写为：“密排嵌合；文字承担主要实形重量，器具填入字组之间的空隙，并以大小差异形成节奏；可见依据是粗实字形与线描器具交替。”具体坐标不是这条关系的必要部分。

不确定的层次允许标为未知或提出候选，不能为了填满六层强行归类。拆解完成也不代表参考方案值得继承，仍需经过取舍、美学判断和印花适配。

### 拆解必填清单与取证

拆解参考图时以下各项必须填写；无法判断时写“未知”，不能省略。

| 项           | 写什么                                                         | 取证方式                           |
| ------------ | -------------------------------------------------------------- | ---------------------------------- |
| 整体调性     | 年代、气质与情绪，一句话                                       | 观察，标推断                       |
| 构图类型     | 平衡方式与构图类型（见“构图类型”）                             | 观察                               |
| 主体与点缀   | 主体是什么；每组点缀的作用、位置与层级（见“主体与点缀的关系”） | 观察；作用标推断，须人确认         |
| 前后层次     | 分几层，每层放什么，谁压住谁                                   | 白底放大核对遮挡关系               |
| 视觉轻重     | 第一眼、第二眼看什么；哪个元素最重、哪个是“大而轻”的背景       | 观察，配合各元素的饱和度与明度对比 |
| 内部疏密     | 稀疏、适中或密集；主体与点缀之间是否留出负空间                 | 内容框内填充率                     |
| 画法         | 着色方式、造型写实度、细节密度（见“画法：着色、造型与细节”）   | 放大局部；强边缘占比与色块数       |
| 色彩         | 色相关系、主次面积、明度与饱和度结构、黑色用量                 | 聚类主色、平均饱和度、黑色占比     |
| 每个文字元素 | 五维、排布方式、是否有描边与阴影、与主体的遮挡关系             | 白底与黑底各放大一次               |
| 表达机制     | 题材本身承载了什么意思；换题材时如何重建                       | 推断，须人确认                     |
| 标志特征     | 一眼认出这张图的 1～3 项                                       | 观察                               |

- **先测后写**：饱和度、黑色占比、内容框填充率、细节密度等可测项先测量，再写描述；描述与测量值冲突时以测量为准。风格刻板印象（如“七十年代就是高饱和”）不能代替测量。
- **多底色取证**：黑色线条、阴影与描边在深色底上不可见，浅色元素在白底上不明显；涉及线条、描边与阴影的观察必须在白底与黑底上各放大核对一次。
- **只写看到的**：每条观察须能在放大图上指出位置；指不出的改标推断或删除。

拆解完成后、生成之前，对照原图逐条自查一遍：每项能否在图上找到依据，是否遗漏了“谁压住谁”“谁最重”这类关系。

### 内容题材与表达意图分开

“夜班快递员”是题材；“夜间独行的安静”和“穿梭城市的速度感”是不同表达意图。相同题材不要求相同构图。

意图指导内容取舍：安静可以依靠舒缓动作和稀疏环境；速度可以依靠前倾动作、方向关系和重复节奏。具体选用步行、骑行或其他动作，是方案选择，不是该题材的永久规则。准备方案时区分必需内容与可删减内容。

### 表达机制与视觉组织的区别

以 DOGTOR 狗医生样本为例：

- 内容题材是狗与医生职业；表达意图是幽默。
- 表达机制是 dog 与 doctor 的语言双关，医生造型帮助理解文字。只替换动物、保留普通职业描述，原来的笑点未必继续成立。
- 视觉组织是角色与上下短句互相解释。上下位置可以改变，只要双关仍能被读懂；反过来，即使保留位置，也不保证机制还在。
- 绘本式线条、颗粒、配色和手写字属于视觉语言；换一种画法可能保留双关，但不再保留原手法的系列感。

同主题装饰款也可以有表达机制。例如 24 号咖啡图通过相关器具与关键词聚合建立主题联想，不需要额外发明故事；文字与器具的密排嵌合、大小变化和空隙互补属于视觉组织，单蓝涂鸦与手写粗字属于视觉语言。换题材时，要重新建立新主题中的语义联系，并保留本次选择继承的构成与语言关系，而不是机械替换图标。

### 视觉组织：描述关系，不固定位置

| 维度       | 可复用的判断                                     | 不应直接固化的实例           |
| ---------- | ------------------------------------------------ | ---------------------------- |
| 焦点与层级 | 首先看到什么？其他内容如何支持它？               | 永远用大头像吸引注意         |
| 重心与平衡 | 视觉重量是否支持目标情绪？稳定或失衡是否有意图？ | 小人物必须放右下角           |
| 节奏与变化 | 重复如何建立联系？差异如何形成停顿或推进？       | 必须切成固定数量的矩形       |
| 对比       | 主要对比发生在哪里？其他区域是否退后？           | 所有区域同时提高反差         |
| 尺度与比例 | 大小关系是否支持主体、叙事与观看尺度？           | 所有图都沿用同一人物占比     |
| 图底与空间 | 空间如何分隔、分组、引导或表达情绪？             | 留白越多越好，或四边必须等宽 |
| 秩序与例外 | 什么建立共同规则？什么有理由打破规则？           | 任何不规则形状都算有设计感   |

这些是本框架整理的工作维度，不是某个院校的官方固定清单，也不是每项都应最大化的美学公式。对比与明暗同时涉及视觉语言。

例如“辅助标题的视觉重量服从主图”适用于图像主导的设计；文字主导的印花可以采用相反层级。必须先确定角色，再选择字高、字重、明暗、行宽和位置。

#### 构图类型

先用两项定下画面骨架：平衡方式与构图类型。两项都描述骨架，不描述具体位置。

| 项       | 取值                                                                                                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 平衡方式 | 对称（左右镜像）、近似对称（骨架对称，细节自由）、非对称平衡（重量不等但稳定）、有意失衡                                                                                                                                                               |
| 构图类型 | 中心式（主体居中，其余围绕）、包围式（文字或图形围成框把主体包住，常见的徽章款）、堆叠式（字与图上下分层）、放射式（从中心向外发散）、对角式（沿斜线形成动势）、嵌合式（字与图互相填空）、散布式（多个等重元素散开，无单一主体）、满版重复（图案铺满） |

构图类型可以组合，例如 STAY WEIRD 是“中心式 + 包围式，近似对称”：主体簇居中，拱形口号从外侧包住主体，底部口号收口。弧度、元素的具体落点属于实例，不进骨架。

#### 主体与点缀的关系

画面用“一个主体 + 点缀与主体的关系”描述，不清点数量。点缀按组记录，每组写三件事：

| 项   | 写什么                                                               | 示例（STAY WEIRD 的花和草）              |
| ---- | -------------------------------------------------------------------- | ---------------------------------------- |
| 作用 | 场景伴生（主体所在的世界里本来就有）、主题聚合、叙事配角、纯装饰节奏 | 场景伴生：蘑菇长在开花的草地上           |
| 位置 | 环绕、包裹、散布、嵌入空隙、指向主体                                 | 环绕主体，并散到口号上                   |
| 层级 | 在主体前或后，压住文字还是被文字压住；视觉上比主体轻在哪里           | 最前层，压住主体边缘和口号；面积小、更简 |

作用是点缀的所指，决定换题材后点缀从哪里来：场景伴生的点缀要换成新主体所在世界的东西，不能沿用原图的花；纯装饰节奏（星光、圆点）不带语义，可以保留。作用没有记录时，换题材会出现两种错误：照搬原图的点缀，或由模型填入与主体无关的风格符号。

数量、大小和具体落点都是实例，只在属于标志特征时才记录。疏密用“稀疏、适中、密集”表达，并以内容框填充率为依据。

#### 内部疏密与画布留白

画布四周的留白属于摆放：上身时由印区和排版重新决定，不是设计手法，不锁定也不参与比较。生成时让设计紧凑，只保留一圈安全边。设计内部的疏密才属于视觉组织，例如主体与字层紧贴、碎片向外散开、元素之间的负空间，这些按关系锁定。

比较疏密时先裁到内容框再计算，画布边距不参与。外轮廓的宽高比由目标印区决定，不从参考图继承。用户分辨不出画布留白与设计疏密，面向用户的预览应展示上身效果，而不是一张画布。

### 色彩：锁关系，不锁色值

| 项         | 记录内容                                           | 示例（TROUT）                                |
| ---------- | -------------------------------------------------- | -------------------------------------------- |
| 色相关系   | 单色、近似色、互补、分裂互补、三角，或中性色加点缀 | 紫、蓝、青、绿近似色主调，橙色互补点睛       |
| 色彩角色   | 主色、辅色、点缀色及大致面积                       | 深藏青描边作骨架，紫与青绿为辅，橙色只在眼睛 |
| 明度结构   | 深浅如何分层，主要明暗对比在哪里                   | 深色描边加浅色填充，明暗跨度大               |
| 饱和度结构 | 哪里鲜、哪里灰                                     | 中等饱和，水花最亮                           |

换题材时按关系重新取色：

1. 从新题材的固有色确定主色相，例如咖啡偏褐、草莓偏红；
2. 按锁定的色相关系推出辅色与点缀色；
3. 用衣身底色校验明度对比与可读性。

题材固有色与参考色值冲突时，保留关系、替换色值。例如 TROUT 的“冷色近似主调 + 暖色互补点睛”用于咖啡题材，可以变为“暖色近似主调 + 冷色互补点睛”。

衣身底色是画面中面积最大的颜色，参与配色关系。深色衣身上，深色描边会与底色融合，需要浅色外描边或调整明度结构；任务书须写明目标底色，或分别准备深色与浅色两套。丝网印刷的色数即分色数，影响成本；深色衣身通常需要白墨打底。具体工艺要求依据商品与印刷方式确认。

### 画法：着色、造型与细节

画法拆成三项分别记录，任何一项不写都会落回模型默认（常见为卡通贴纸或数字厚涂）。

| 项         | 记录内容                                                                                   | 示例                                                                      |
| ---------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 着色方式   | 平涂、赛璐璐分色、勾墨加平涂、厚涂、版画排线、水彩、丝网半调等；线条的形状、粗细与出现位置 | TROUT：深色粗轮廓；暗部集中尖头收笔的楔形墨线，亮部大块平涂，硬边白色高光 |
| 造型写实度 | 写实比例、半写实或卡通比例                                                                 | TROUT：写实比例与结构                                                     |
| 细节密度   | 细节靠什么撑起（形状数量还是色阶），大致多少                                               | TROUT 按 481px 宽：强边缘占比约 0.36，色块约 2300                         |

关键在线条的**形状与位置**，而不是有没有线：同样是“线”，均匀细排线读作铜版画，暗部楔形笔触读作勾墨插画。“少色阶”不等于“少细节”，描述时不能用“少、只、简单”等减法措辞概括整体。

### 字体：按维度选择

字体不用一句风格描述概括，而是拆成可以逐项选择的维度。主标、副标、小标、圆章等文字元素分别选择。

| 维度     | 回答什么                         | 词表                                                                                                                                                                                                                                 |
| -------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 结构类型 | 字母如何构造                     | 无衬线：人文、几何、新怪诞、怪诞、圆角、超椭圆、刻石；衬线：旧式、过渡、现代、迪多、苏格兰、粗胖；粗衬线：克拉伦登、几何、人文；手写：正式、非正式、手写、直立手写；等宽。中文：宋（明）、黑、楷、仿宋、圆、书法（行、隶、篆）、手写 |
| 结构参数 | 同一类型内的差异                 | 字重、字宽、粗细对比、x 高度、倾斜                                                                                                                                                                                                   |
| 主题     | 来自哪种工艺或年代               | 木活字、托斯卡纳、装饰艺术、新艺术、哥特、做旧、模板、内线、阴影、笔刷、像素、科技、泡泡、中世纪、古怪；候选词：学院运动队字                                                                                                         |
| 字效     | 字形之外的处理                   | 填充（条纹、渐变、纹理）、描边与外描边、投影与立体、变形（拱形、透视）、做旧                                                                                                                                                         |
| 气质     | 给人什么感觉，可附 0～100 的程度 | 粗犷、笨拙、响亮、复古、商务、平静、能干、真诚、俏皮、拘谨、快乐、活力、童趣、可爱、艺术、兴奋、未来、创新、华丽、精致                                                                                                               |

西文的结构类型、主题与气质词表取自 [Google Fonts 标签体系](https://googlefonts.github.io/gf-guide/tags.html)（2024 年起用于字体上架）。该体系每款字体打 2～6 个标签，至少包含一个外观或气质标签和一个结构标签，并以百分比表示程度。按历史时期分组的 Vox-ATypI 分类已于 2021 年被 [ATypI 撤销背书](https://atypi.org/2021/04/27/atypi-de-adopted-the-vox-atypi-typeface-classification-system/)，它只说明来源年代、不说明观感，不作为主分类。中文类型沿用行业惯例，尚无同等公开的标签体系。

#### 字形与主体的关系

只换结构类型、而主题、字效与气质不变时，换了题材的文字看起来仍是同一套，与主体没有关系。字体形态应从题材推出：

| 关联方式 | 含义                               | 示例                                                   |
| -------- | ---------------------------------- | ------------------------------------------------------ |
| 工艺关联 | 采用该题材行业常见的字体与制作工艺 | 咖啡：烘焙厂麻袋印章、餐馆手绘招牌；钓鱼：渔具店木活字 |
| 材质关联 | 笔画由主体的材质构成或带有其质感   | 咖啡：流淌的液体笔画；猫：毛绒边缘                     |
| 形态关联 | 笔画借用主体的形状或动作           | 猫：尾巴卷曲的收笔；鱼：鱼鳍形衬线                     |
| 无关联   | 通用展示字，不随题材变化           | 只适用于刻意统一的系列字标                             |

关联强度可以分层：主标强关联，副标与小标弱关联，避免整体可读性下降。

#### 每个文字元素分别填写

主标、副标、小标、圆章等每个文字元素都按五个维度填写，并补充两项关系；只给主标填写时，其余元素会落回模型默认的通用字，例如所有副标都变成同一种带飘带的招牌笔刷体。

| 关系项           | 选项                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| 与主体的关系     | 关联方式（工艺、材质、形态、无关联）与强度；同一设计中的不同元素宜换用不同关联方式，避免重复           |
| 与其他文字的关系 | 同源（同一工艺或材质，形成一套）、对比（结构类型或书写方式相反，拉开层级）、从属（弱化处理，不抢主标） |

示例：

| 元素       | 与主体                 | 与其他文字           | 咖啡                 | 猫                 |
| ---------- | ---------------------- | -------------------- | -------------------- | ------------------ |
| 主标       | 强关联                 | —                    | 木活字麻袋印章粗衬线 | 毛绒虎斑圆角字     |
| 副标       | 弱关联，换一种关联方式 | 与主标对比，不抢主标 | 咖啡馆黑板菜单粉笔字 | 毛线绕成的手写字   |
| 小标、圆章 | 随主标                 | 与主标同源，从属     | 与主标同一套印章工艺 | 圆章用爪印代替圆点 |

#### 锁定方式

| 项                                                               | 手法款通常                     |
| ---------------------------------------------------------------- | ------------------------------ |
| 字层对比，即各文字元素结构类型之间的对比（如粗重印刷体对手写体） | 锁定                           |
| 气质                                                             | 锁定，作为系列的共同感受       |
| 外描边等服务印花适配的字效                                       | 锁定                           |
| 结构类型、主题与其余字效                                         | 按字形与主体的关系，从题材推出 |

生成模型会把字体与风格标签绑定；描述字体时按上述维度写具体取值，不写风格标签。生成图中的文字是画出来的近似字形，不是真实字体，难以精确控制，商用授权也无法确认；字体形态重要时，生成阶段可以不带字或只放占位字，最后用真实字体排版。

### 视觉语言与 IP 身份

有 IP 时，先从参考图中确认影响识别的外观特征，再指定哪些允许改变。不能仅凭未知角色的名字猜测设定。IP 识别点同时依赖内容特征与造型，不能只归为画风。

例如本次输入形象的黑色长发与低马尾、方框眼镜、可见黄色眼睛、白衬衫和黑马甲，可以作为当前试验的身份约束；动作、视角和场景可以重新设计。服装是否属于永久身份特征，仍取决于该 IP 的具体要求，不能泛化为所有角色都不得换装。

参考图中的问号、小涂鸦等元素需要判断是角色设定还是附属表达，不能默认全部继承。

### 印花适配同时包含视觉与工艺

视觉适配关注图形轮廓与衣身的关系、远近观看时的识别点、实际印花比例，以及褶皱对关键内容的影响。外轮廓的宽高比按目标印区确定。胸前小图、前胸主图与后背大图需要分别取舍内容，不能只缩放同一张完整插画。

工艺适配关注实际尺寸下的细线、小字、色块、渐变、边缘与底色处理。清晰度档位以 `src/modules/product-templates/print-clarity.ts`（路径相对本应用目录）为准；线宽、字高等其他阈值依据商品、面料和印刷方式确认，不在未知条件下统一指定。

同一款图常售多种底色。白色或浅色主体在白底上消失，黑色线稿在黑底上消失，矩形背景在异色衣身上成为贴片；任务书须写明目标底色范围，或说明需要准备哪些底色变体。

商品或工艺尚未确定时，记录假设和待验证项，结果标为设计概念。白底预览不能视为透明底成品，样机效果也不能替代实际印制验证。

### 深浅衣服（2026-11-10 定）

DTF、DTG 会先印一层白底，所以彩色图案在深色衣服上本身能显出来。真正的失败只有两类：深色线条和字在深色面料上消失，白色或很浅的元素在白色面料上消失。

**主品类**：模板先为服装（T 恤）设计。杯子、手机壳、帆布袋、海报等其他载体，从透明画布上的母版往下游适配（按印区填底色、摆放），不在拆解时分别设计。按品类、按载体收集素材并写各自的工作流与提示词，是以后的方向，现在不做。

**拆解时做（规则 1、2）**

1. **优先做与衣服色无关的设计。**
   - 设计贴片自带底色，任何衣服色都成立。
   - 独立图形可以加贴纸白边，文字可以加描边，把图案和面料隔开。
   - 不加的情况：极简线稿等描边会毁掉画法的风格，宁可走规则 2 限定衣服色。
2. **做不到与衣服色无关时，定适用衣服色。** 用 `accept.py` 分别判定白衣、黑衣，把结论记成模板的适用衣服颜色：浅色可用、深色可用、通用。

`accept.py` 目前没有衣服色参数，也不必有：它的检查里“深色衣服上消失的独立深色元素”“深色衣服上大面积消失”对应黑衣，“白色衣服上消失”对应白衣，一次运行同时给出两种结论。判读方式：

| 深衣检查（两项） | 白衣检查 | 适用衣服颜色 |
| ---------------- | -------- | ------------ |
| 通过             | 通过     | 通用         |
| 通过             | 不通过   | 深色可用     |
| 不通过           | 通过     | 浅色可用     |
| 都不通过         | 都不通过 | 回到规则 1 改造；改不了按“不适合衣服”处理 |

设计贴片形态下三项只记录不判定，适用衣服色记通用，边框与衣服色是否分得清由人看 `--preview`。深色底生成后镂空的做法（见下文“渐变与光晕的印法”）固定标深色可用。

**记在哪里**：`designSpec.printFit` 现有 `verdict`、`lightIsMood`、`recommendedMethod`，没有衣服色字段，`recommendedMethod` 是自由文本，不能当结构化字段用。适用衣服色应作为 `printFit` 的新字段（暂名 `garmentTone: any | light | dark`）。**这是待定的 schema 变更**：`printFit` 是 `.strict()`，加字段要改 `design-spec-schema.ts`、导入 schema、`to_v4.py`、后台只读展示与 v4 spec 第 3 节；落地前，拆解结论先记在 `notes.md`，不写进导入 JSON。下游 POD 选款按它推荐或限制衣服色（浅色可用的图禁选深色衣服，或提示效果会变差），该部分尚未实现。

**生成同款时做（规则 3、4，只定规范，以后实现）**

衣服色适配不在做模板时处理，而在生成同款之后由用户发起：结果放到所选深色（或白色）衣服上不好看，用户可以点「优化成深色衣服版」或「优化成浅色衣服版」，走现有“编辑这张图”（图生图 EDIT）链路，使用一套固定指令。

| 可以改                                                                                 | 不能改                                                                       |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 与面料冲突的元素的颜色：深色线稿改浅色、加描边或贴纸白边、把近黑的字换成浅色（反向同理） | 构图与位置、主体是谁、文字内容                                               |
| 单一油墨的线稿可以直接确定性换墨色，不走模型，更省                                     | 物件固有色：咖啡不能变绿，朱红不能变粉；原因见下                             |

- 不能用通用的后处理换色。方法正本已否决：[配色只在生成时约束](#反推试验2026-11-04)，后处理换色会把物件本色一起换掉（咖啡变绿）、颜色变名、文字对比度下降。本功能只动与面料冲突的元素，物件本色不动，因此走带指令的编辑，不走全图换色。
- 验收：对结果图再跑一次 `accept.py`，按目标衣服色看对应检查项必须通过；再看 `--preview` 的目标衣服色一栏，由人确认没有改动构图、主体与文字。
- 计费：优化结果是用户明确要求的一次新结果，按现有编辑的任务、点数与消耗规则处理，不另定价，也不替换原结果。
- 实现前不开放入口，也不在模板数据里预存深浅两个版本。

### 印花版：替换封面与参考图（2026-11-10 定）

同款档生成时，`same_design` 把模板原图作为第 1 张图附给模型，模型会强烈保留它；封面本身不能直接印（带整幅背景、深色元素贴着透明、边缘发虚）时，生成结果会把这些问题原样复现。

- 对封面不能直接印的模板，拆解同时产出一张「印花版」：按推荐印花形态做成的透明画布印花母版（独立图形的外轮廓、设计贴片的边框都按本文规则做好）。
- 印花版经人审并通过 `accept.py` 后，**同时替换**模板的展示封面和送给模型的参考图，两处用同一张，不留两套。
- 封面本来就能直接印的，不做印花版。
- 印花版只改形态、边缘、配色与光晕，不改构图、主体和标志特征；人审时与原封面并排看。

**两条路并行**：找更好的数据，和把不好的数据改造成好模板，一起在存量升级阶段做（见 [v4 Spec](print-design-semantics-v4-spec.md) 第 8 节第 4 步）。新收的素材按本文标准挑，已有的差模板按上面的印花版改造，不只靠其中一条。

## 结构化与反推

目标是把参考图拆成六层结构化数据，再用这份数据生成同类新图。结构化服务于迁移，不服务于还原。

### 提取

参数分三类，可靠性不同：

| 类型   | 覆盖内容                                                             | 提取方式                             | 可靠性与用途                             |
| ------ | -------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------- |
| 可测量 | 底的类型、主色及面积、内容框内填充率、重心、明度跨度、最小线宽与字高 | 像素统计、聚类与分割，不经语言模型   | 同一张图结果一致；用于底线检查和发现问题 |
| 可描述 | 内容与关系、手法类型、外轮廓、色相关系、字层与字体各维度、线条语言   | 视觉语言模型按固定字段与当前词表填写 | 措辞会漂移，须检查多次提取的一致性       |
| 需判断 | 意境、承重关系、参考元素的继承／借鉴／舍弃、失衡是否有意             | 无法提取；模型只给候选，由人确认     | 属于设计决策，不是提取结果               |

- 位置、比例、占比等几何量用计算获得，不交给语言模型估计。
- 疏密类参数先裁到内容框再计算，避免画布边距混入；色数先聚类再计数，避免渐变与纹理抬高结果。
- 测量值是证据，不是还原目标。验收看方向是否保持（仍疏朗、仍暗、仍克制），不追数值。
- 提取得到的是单张图的实例值；把实例抽象为关系或区间（如“主体主导、重心偏低”）属于需判断类。
- 不透明底的参考图：取画布外圈的中位色作底色，与底色足够接近的像素算作底；留底元素因此不计入填充，需在数据里单列颜色角色。照片类、满幅封面的填充率只作参考。
- 版面框目前靠目测后叠回原图核对；文字框与主体轮廓尚未接入自动识别。

### 结构化而不锁死

结构化数据不能变成只能还原原图的模具。三条约束：

- **取值不写死**：用关系、方向和区间描述，如“主体主导”“重心偏低”“单色到三色”；坐标、像素尺寸和精确占比只作为证据保留，不作为反推目标。
- **锁关系不锁实例**：疏密、色彩与字体分别按“内部疏密与画布留白”“色彩：锁关系，不锁色值”“字体：按维度选择”拆开，只锁其中的关系项。
- **结构可扩展**：手法、机制、视觉语言等词表可以增补。词表外的特征用自由文字记录并标为候选词，反复出现后再并入词表；无法判断的字段标为未知，不强行归类。

### 反推同类新图

反推按锁定方案使用数据：不变量写成约束，可变项不写入或主动替换。一份结构化数据配合不同的可变项取值，可以产出多张不同的图。

- 构图骨架可以写成版面 JSON（每个元素的角色、内容、bbox、前后层级，加上元素之间的遮挡关系）直接放进提示词，也可以由同一份 JSON 渲染成草图作参考图。两种方式下，模型都照做元素的相对位置与遮挡，与原图不同的对角非对称骨架也照做；框的精确边界不被遵守：字比框大，主体越出框，草图里空着的区域会被填满。把留白写成 JSON 中的一个元素能否保住空白，尚待验证。
- 草图只用虚线轮廓，不填色：灰块会被画成文字底板，提示词写了“不要画出来”也挡不住；虚线框没有被画出来。分元素合成的效果尚待验证。
- 成功判据不是像不像原图。对新图重新提取一遍：不变量应与原数据一致；可变项应当不同。若可变项也一致，说明结果接近复刻。
- 未写入的可变项会由模型默认偏好填充，而不是保持中立。需要变化时主动给出新取值，例如为每个题材指定字体的结构类型、主题与字效。
- 风格标签会带入内容和字形，例如“户外运动”会让咖啡杯出现雪山图案。反推描述只写具体特征。
- “压住约三分之一”等程度描述执行不稳定，只作验收判据，不要求精确兑现。
- 字图咬合须写明前后层级（主体在前遮挡文字，或文字在前）；只写“重叠”时，模型可能反转遮挡方向。
- 题材的物理属性会压过锁定的组织关系，例如倾倒的液体天然竖直，削弱对角动势。与颜色冲突一样，须记录本次让题材还是让关系让步。
- 按关系锁色后，同一系列的颜色可以完全不同，系列感改由结构、字层与外描边承担；需要同色系列时改锁色值。

### 数据格式

一张参考图拆成一份 JSON，分整体层与元素层，另加档位与迁移条目。

**档位**决定锁定范围、附不附原图和画幅，先定档位再拆：

| 档位     | 锁定                                 | 附图               | 画幅       | 适用                                       |
| -------- | ------------------------------------ | ------------------ | ---------- | ------------------------------------------ |
| 同手法   | 整体层，以及各元素的作用与关系       | 不附               | 由印区决定 | 从参考图做同类新图；只有风格描述的配方模板 |
| 标志特征 | 同上，再锁 1～3 项实例               | 不附               | 由印区决定 | 既要认得出参考，又要贴合新题材             |
| 同款     | 同上，再锁具体颜色、姿态与大部分实例 | 附原图，并写明颜色 | 跟随原图   | 有模板原图、要“同款换主体”的模板           |

默认：有模板原图的用同款档，其余用同手法档。没有印区信息时，画幅沿用封面比例。线上模板对比中，同款类模板不附图时拆解法不如模板配方；附原图并写明颜色后持平或更好，且没有带进原主体外形或原配色。

**整体层**记录整张图共有、换题材时通常不变的东西：

| 维度     | 写什么                                                                               | 写法要求                                                              |
| -------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 调性     | 年代、气质、情绪，一句话                                                             | 不用会带出内容的名称（“汽水广告”“咖啡馆”“七十年代迷幻”）              |
| 画法     | 着色方式、线条质感、线条相对粗细与深浅、细部画法（五官、高光）、细节密度             | 对任何主体都成立；线条深浅按测量写（如“近黑细线”），否则会画浅        |
| 配色关系 | 每个颜色角色的用途与面积、冷暖，以及测得的深浅与鲜艳档位                             | 只写关系与档位；其他字段用 {色:角色名} 引用颜色，具体颜色写进迁移条目 |
| 构图骨架 | 画幅、平衡、构图类型、层次、视觉轻重、疏密、版面 JSON（元素角色、bbox、z、遮挡关系） | 尺度用框或相对比例表达，不写数量                                      |
| 印花形态 | 独立图形、矩形贴片（设计贴片）或出血裁切；拆解时定一个推荐形态，不留备选            | 见下文“印花形态怎么选”                                                |
| 外轮廓   | 收法与收形元素：图案的边缘怎样收成一个形状；设计贴片的边框也是收形元素               | 收形元素写成要画出来的东西，进版面 JSON；只写形状，边缘质感随画法     |
| 表达机制 | 画面靠什么成立，换题材时怎么重建                                                     | 推断，须人确认                                                        |

**元素层**为主体、每组点缀、每个文字元素和纯装饰各记一份，分三栏：

| 栏           | 含义                       | 例：Cold Soda 的主体                           |
| ------------ | -------------------------- | ---------------------------------------------- |
| 作用（所指） | 它在图里起什么作用         | 产品本身做画面中心，自带品牌标签               |
| 关系         | 位置、层级、尺度、与谁遮挡 | 居中略倾斜，压住上下两行大字的边缘             |
| 实例（能指） | 原图里它具体长什么样       | 汽水瓶盖，一圈锯齿边，月牙高光，印着 Soda 标签 |

文字元素如果内容是关于主体的（词头、释义、名字），标“跟随主体”：用户换了主体而没填这一处时，不写默认字，改由模型按新主体来写；固定文字（品牌词、口号）不标。

主体另记：“原物”（原图主体是什么）与“外形特征”（只写原物独有的外形，如瓶盖的锯齿边；“粉色鼻头”这类新主体也可能有的特征不写，否则会误伤新主体），供检查与附图说明使用；“固有色策略”，默认“保留”，产品、器物这类本来就随设计着色的主体设为“随配色”；同款档另记“姿态”。限定套色的模板（配色由选项给出、全图只用这几种颜色）本来就要给主体上色，固有色策略设为“随配色”。配色角色可以写“作用于”哪些元素，检查按它判断，而不是在用途文字里找“主体”二字；画在主体身上、但属于画法的颜色（腮红、高光）标为“属于画法”，不算给主体上色。

不透明底封面上与底色相同的元素（纸色镂空字、留底的浪花）称为留底元素。生成图是透明底，它们必须当一种颜色来画，因此拆解时给它们一个颜色角色。

**迁移条目**每个新题材一条，只填会随题材变化的值：新主体（身份与外形）、主体外形、姿态、主体固有色、场景伴生点缀的来源、指定内容（用户指定的非文字内容，按元素填写，原样画出）、每个文字元素的新文字、每个颜色角色的具体颜色（可附色值）、需要重建的趣味。

每一项按三个问题归位：

1. 这是“怎么画”，还是“画的是什么”？怎么画归画法，全局通用；画的是什么归该元素的实例，属于原图那个物件，不迁移。
2. 换了题材，它该不该变？不该变的写进整体层；该变的写进迁移条目。例如“好吃极了”的油亮高光是“好吃”的表达，换成“困死了”就该变。
3. 这是作用，还是实例？作用与关系进数据；实例只作证据，默认不进提示词，同款与标志特征档才把指定的几项实例写进去。

写法规则：

- 会进提示词的字段里不出现原图物件的名词与外形词。把“徽章”写进主体外形后，附原图时拉面碗长出了瓶盖的锯齿边。
- 点缀与装饰的外形从新题材推出，不描述原图里的形状。写成“大块卷曲、带钩状尖尾的形状”后，模型把锦鲤图的浪花画了回来；这类外形描述编译检查拦不住，拆解后要人看一遍。
- 主体保持本来的颜色：用户指定的配色只用在边框、底板、文字和装饰上。配色分给主体后，浣熊被染成焦橙，看起来像小熊猫。
- 姿态只写在一处：同款档写在主体元素里锁住，其余档写在迁移条目；附原图时必须写明，否则会沿用原图的姿态。迁移条目的“主体”只写身份与外形。
- 主体外形写成“保持它自己的标准外形”，再由迁移条目给出新主体的样子。
- 不用抽象风格词，写看得见的特征。
- 数量不写；新题材的主体数量与骨架冲突时（两条锦鲤换成一只浣熊），以新数量为准，重排骨架里依赖数量的部分（对称、环绕）。
- 用户替换了承担视觉作用的元素时，保留它的作用：封面的朱红盘沿是全图颜色最重的一圈，用户把盘子换成竹蒸笼后，竹蒸笼用竹子本色，但仍画成全图颜色最重的一圈。
- 表达机制写成能照着画的画面关系：“主体蜷成食物形状”要写成“主体与食物一样大、一样颜色、排在同一圈里，只露出头和尾巴”；只写机制名称时，模型把主体画得比食物大一圈，混入感就没了。
- 道具上自带的字（报纸、书页、包装上的小字）画成看不清的灰色笔划纹理，不算进文字白名单；数据里给该元素标“带字道具”，编译会把白名单改为“画面里可读的字只有……”。需要用户指定内容的元素，描述只写样式，并用 {内容} 标出用户内容插入的位置。
- 标志特征默认保留：承载原图笑点或识别的实例（如“我是一片吐司”的吐司脸）即使在新文字下双关失效，也照样保留；只有用户明确要求改动时才改。这类锁定的实例列进“锁定实例”，编译的泄漏警告不会再报它们。
- 用户输入优先，但不能跨画法大类：模板文字、选项与封面画面不一致时，画法按封面实际画的，内容与颜色按用户输入。用户要求与原图画法跨大类（二维扁平改成三维立体、线描改成写实照片）时，判为不合格案例，不做。
- 颜色分给哪个角色：用户给出的几种颜色，默认按封面的明暗结构对应——最深的颜色给封面里最深的角色，依此类推，保持原图的明暗关系；列色顺序不作依据。此条尚待验证。
- 文字写白名单：除列出的文字外，画面里不出现任何字。
- 透明底打不出半透明，先分清光感是不是意境：
  - 不是意境（模型自己加的雾、阴影、柔焦）：数据里不写光晕、发光、烟雾、朦胧、柔焦、虚化、半透明、淡出这类词，改写成能画实的形状或颗粒；编译检查拦下这类词，画法段末固定加“每个形状都是实心的，边缘清楚；明暗和光感用颜色深浅画在形状内部”。用户在选项里填的内容照写，只警告。
  - 是意境（梦幻夜光、逆光、柔光）：不要实心化。实心化再切边后光晕没了、切口发硬发灰，验收合格但难看。照原图在深色底上生成，印前把底色镂空、光晕转成网点或颗粒，标“适用深色衣服”；或收成设计贴片（见“印花形态怎么选”），光晕留在贴片里。数据里标出光感属于意境与所选印法。

**印花形态怎么选**（2026-11-10 定）：每个模板在拆解时只定一个推荐形态，不做备选变体，用户不能切换。三种形态按封面的样子选：

| 封面是什么                                           | 形态                 | 要求                                                                                                         |
| ---------------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------ |
| 有完整外形的图案（角色、贴纸、徽章、文字造型）       | 独立图形             | 外轮廓要设计：元素本身的剪影，或用收形元素收成一个形状；画布外圈留空                                         |
| 整幅背景、场景、海报、词典页、满幅水彩               | 矩形贴片（设计贴片） | 必须有设计过的边框，边框写成收形元素；贴片不透明，贴片以外透明；伸出边框的元素推荐但不必需                   |
| 主体被画布切开（胸像、半身）且就该切开               | 出血裁切             | 写明从哪条边切、切口怎么收；直接切开不好看时改成独立图形加一种收法                                           |

**矩形贴片只接受“设计过的贴片”**：数据里的枚举名仍是 `rect_patch` / 矩形贴片，含义从“画布直接裁出的矩形”改为“透明画布上一块边框经过设计的不透明贴片”。
- 边框必须设计：包边（实线或金线描边）、撕边、齿边（邮票边）、圆角、票根缺口、拍立得相框、拱窗等，不能是画布直接裁出的直角矩形；轮廓最好不是单纯的矩形（圆角、齿边、缺口都算）。边框写成类别“收形”的元素，同时进版面 JSON；没有收形元素的矩形贴片导入时被拒绝。
- 伸出边框的元素（标题字压框或出框、挂角徽章、标签、飘带）推荐、不必需；有就写进元素层和版面 JSON，它们画在边框之上、可以越出贴片，编译提示词统一写“伸出边框的元素画在边框之上”。数据里没有的不凭空添加。
- 生成时画布请求透明：贴片以外完全透明，没有底色、阴影、渐变；贴片自己的底色是不透明的实心色（写成颜色角色，由收形元素引用）。
- 光感属于意境的整幅夜景、逆光，用这一形态收成贴片，光感留在贴片里；背景不再因此改成不透明画布。贴片自带底色，在深色或白色衣服上不会像独立图形那样消失，但边框与衣服色是否分得清，要看上身预览。
- 同款档默认保留封面的整幅形态，所以整幅背景的同款模板选矩形贴片；同手法与标志特征档若封面是整幅背景，按需要重画成独立图形，不要硬做贴片。

**外轮廓**：图案的边缘怎样收成一个形状，属于视觉组织（外轮廓和负形），在印花适配里检查。常见收法：

| 收法     | 收形元素                                   | 适合                       |
| -------- | ------------------------------------------ | -------------------------- |
| 自然剪影 | 无，外轮廓就是元素本身的轮廓               | 多数独立图形               |
| 底托     | 压在切口上的飘带、文字条、地面线           | 胸像、纪念款               |
| 容器     | 圆框、徽章、拱窗框，框边就是切口           | 复古、徽章调性             |
| 渐隐     | 由密到疏散开（网点变小变稀、毛尖、飞白）   | 网点、水彩、厚涂           |
| 自然收形 | 穿上的衣服，下缘是衣服收成的圆弧           | 写实肖像、时装肖像         |
| 形状蒙版 | 拱形、圆形等形状，里面铺底色，没有框线     | 照片感、海报感             |
| 异形裁切 | 撕纸边、波浪边、斜切                       | 拼贴、手作感               |
| 笔刷遮罩 | 一大笔干刷形状，画面只在笔刷内             | 手绘、做旧                 |

收形元素写进元素层（类别“收形”）和版面 JSON，编译时在点缀后单列“外轮廓”段。封面本身被画布切开（如吐司狗的身体被底边切掉）时：同款档默认照原图切开，印花形态记为“出血裁切”，写明从哪条边切、切口怎么收，验收时那条边不算截断；直接切开不好看时改用上表的一种收法，印花形态记为“独立图形”。附原图时，只写一句形态压不过原图（两个胸像模板写“完整落在画布内”，八张仍全部切开）；写成收形元素并在附图说明里把外轮廓列为以描述为准后，七种收法都画出来了。渐隐和笔刷遮罩容易把边缘画成半透明，须按印花验收检查。

**底线与同款冲突**：同款档以模板为准，满幅背景、海报这类形态保留为设计贴片（边框要设计，不是原样保留一块画布裁出的矩形），在验收里标出“矩形贴片”；同手法与标志特征档以印花底线为准，画成外轮廓完整的独立图形。

与六层的对应：内容题材对应元素实例与迁移条目；表达意图与机制对应表达机制；视觉组织对应构图骨架、外轮廓与元素关系；视觉语言对应画法、配色关系与字形；印花适配对应印花形态，其余留给上身验收。

提示词由编译脚本从这份数据生成。脚本先检查，出现以下情况就报错、不出提示词：会进提示词的描述字段里有原物词或抽象风格词；颜色占位引用了不存在的角色；固有色策略为“保留”而配色用途写了主体；印花形态为矩形贴片却没有收形元素（贴片的边框必须设计）。另有三类警告：档位与附图方式不一致；主体或场景伴生点缀的实例短语出现在提示词里（提示可能的外形泄漏，由人复核；锁定实例与标志特征不报）；独立图形里出现“撑满画面”这类措辞（图案容易碰到画布边）。通过后按固定顺序组装（矩形贴片的整体收尾句固定为“设计贴片：透明画布、不透明的实心贴片、贴片以外完全透明、伸出边框的元素画在边框之上”），把迁移条目的值填进去，只替换颜色占位，不加数据以外的措辞。附原图时自动生成一句附图说明，并点名原主体；有收形元素时，附图说明把外轮廓也列为以描述为准；附主体照片时写明只取主体的身份、外形和花色。同一份数据每次编译结果相同，生成出了问题可以追到具体字段。

### 提示词编译

结构化的是数据，不是提示词。发给模型的提示词由数据编译成自然语言画面描述：

- **顺序**：开头一句明确指令（画一张 T 恤印花图案、什么风格、主体是什么、画面里写哪些字）→ 主体 → 文字 → 点缀 → 外轮廓 → 版面 → 画法 → 配色 → 文字白名单。要画的内容在前，画法与配色这类参考在后。
- **每样东西只写一处**：版面 JSON 只管位置与遮挡；元素的样子写在各自段落；配色按“颜色：用途”一次写完，文字与点缀里的颜色直接写色名，不让模型自己对应“主色就是墨绿”。
- **构图骨架**：平衡方式、构图类型和前后层次必须写出。只写“构图自由”时，模型会退回自己的默认版式（标题在上、插画在下），参考图的骨架随之丢失。要构图有变化，放开的是实例（弧度、落点、大小），不是骨架。
- **主体详写**：比例、动作、花纹、细节与高光处理都写出；主体只写一句时，模型会把注意力放到篇幅更长的文字说明上。
- **点缀从作用推出**：按点缀的作用为新题材给出新的点缀，例如场景伴生的点缀写成“咖啡桌上本来会有的东西”；不沿用原图的点缀，也不写数量。提示词里举的例子会被全部原样画出，并固定成同一组合，因此例子只在需要锁定实例时给出。只写来源时，模型能自己选出合理且每张不同的点缀，但件数会变多、画面更满。
- **正向描述**：写该画什么、画多少；“没有黑线”写成“轮廓线用主色勾”，“不画腮红”写成“脸颊保持白色”，文字白名单写成“画面里的字只有上面列出的这些”。
- **不用抽象风格词代替具体画法**：“Q 版”会调出萌系的腮红和高光大眼，“满版”会调出小图标铺成的壁纸，“小幽默”会调出带笑脸的物件。要写看得见的特征，例如“眼睛是大圆圈加一个小黑点，嘴是一条线”。
- **文字白名单**：写明“除上面列出的文字外，画面里不出现任何字”；只写“只出现上面写到的内容”时，店铺类题材会自动加上招牌字。
- **不写元语言**：“标志特征”“锁定”“关系”等是给人看的管理语言，编译时转成画面描述。
- **不写流程内容**：透明底由生成参数控制，边距大小与摆放由印区处理，不进提示词。但要写一句完整性要求：“整个图案完整地落在画布内”；不写时，徽牌的底座被画布截掉，截掉的部分后续裁边救不回来。
- **没有文字的设计**：指令句写“画面里没有任何文字”，省略文字段。
- **语言**：中文与英文均可；中文便于人审阅与修改，必要的专业术语可在括号中附英文。
- **参考图**：按档位决定，见“数据格式”的档位表。几种附图方式的已知效果：
  - 不附图：配色与内容完全由数据决定；画法只靠文字，细节最弱。
  - 整张原图并写明颜色：画法最像，构图跟随原图，颜色照指定；配色交给模型自选时，原图配色会被带走。附图说明要如实写“照它的画法和版面来画”，并点名原主体。
  - 主体照片：只取照片里主体的身份、外形与花色，画法、构图和背景按描述。
  - 灰度风格样张（原图局部拼贴并去色）：不推荐。它能传线条与笔触，但会把画面拉浅拉灰，写明颜色后饱和度仍明显偏低。
  - 需要不同于原图的构图时不附原图，由版面 JSON 控制。
  - 封面带整幅背景或光晕时，附原图会把它们一起画进来，写法管不住：两个这类模板附原图，旧写法和实心写法八张全是整块矩形或满幅底。要整幅就照同款档做设计贴片（透明画布、不透明的设计过边框的贴片）；要独立图形就不附原图，或附去掉背景的原图，且抠图边缘要切实（软边抠图会把光晕带回来）。
  - 以原图为编辑底图逐件替换：把原图当编辑对象，要求每件物件换成新题材的东西、保持位置大小和线条粗细。满铺涂鸦的物件尺度只有这样才保住（填充 0.37～0.40，原图 0.42；文字描述、附原图作参考、物件框都无效）。代价是版面完全照搬，属于同款档；新文字比原文长时会写错（“FRESH”塞进“YA”的位置只写出“FRE”），原图的字符也会漏过来（“CAFÉ”的重音符号落到“BREAD”上）。
- **点缀色**：写“柔和”仍会偏艳（拉面的珊瑚橙彩度 64～67，原图点缀约 45）。点缀色附色值，并写具体形容（如“带灰的浅珊瑚橙”）；效果待验证。

## 有参考图时先做取舍

客观分析与设计决策分别记录，避免把参考图的特点全部升级为硬约束。

| 处理方式   | 判断依据                 | 示例                                       |
| ---------- | ------------------------ | ------------------------------------------ |
| 必须继承   | 明确要求或身份识别所必需 | 指定角色的关键外观、必须准确出现的文字     |
| 可以借鉴   | 支持本次表达和商品条件   | 线条语言、配色关系、某种构成方法           |
| 改进或舍弃 | 削弱表达、美学或商品适配 | 拥挤文字、无意图的失衡、缩小后不可读的细节 |

只有在明确要求复刻版式时，才把参考图的位置关系作为保真目标。新设计应允许重新选择构成方法；参考图本身不够好看时，也能保留有价值的内容并重组画面。

带第三方 IP、图库水印或来源不明的参考只能借鉴手法与关系，不能作为素材或复刻对象。

## 生成前的设计任务书

每次准备一份简短任务书。未确定的信息写明假设，不虚构已知条件。

1. **保留对象**：本次保留手法、意境还是身份，复刻刻度（同款／标志特征／同手法）及锁定的标志特征，以及希望产生的穿着效果。
2. **商品条件**：目标商品、底色范围、印区、实际尺度与已知工艺；缺失条件单列。
3. **六层决策**：逐层写明不变量与可变项。

   | 层次     | 写什么                                                                 |
   | -------- | ---------------------------------------------------------------------- |
   | 内容题材 | 必需元素、准确文字、可删减内容，以及动作、场景等允许变化的范围         |
   | 表达意图 | 主要与次要意图，不应被削弱的重点；装饰款可写装饰趣味                   |
   | 表达机制 | 依靠的机制；替换题材时如何在新题材中重建                               |
   | 视觉组织 | 焦点与重心、层级、主要对比、节奏、空间与字体关系，以及它们如何服务意图 |
   | 视觉语言 | IP 识别点、画风、线条、配色、字体气质与质感                            |
   | 印花适配 | 由商品条件产生的内容取舍与布局要求                                     |

4. **验证方式**：各层完成标准，以及仍需上身预览或打样确认的部分。

具体布局可以在任务书基础上形成多个候选，但候选的摆放方案不回写为所有设计必须遵守的规则。

## 生成后独立验收

预处理定义要求；验收检查实际结果。提示词包含某项要求，不证明图片已经执行。

| 验收项         | 检查内容                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------ |
| 内容题材       | 主体、动作、道具、文字及其关系是否正确，有无遗漏或错误                                     |
| 表达意图与机制 | 不看任务书时，是否传达目标意图；依靠的机制能否被读懂                                       |
| 视觉组织       | 底线是否满足；层级、重心、对比、节奏与空间是否协同，有无无意图的拥挤、截断或竞争           |
| 视觉语言       | IP 是否可识别，指定画风是否保留，有无未经允许的改动                                        |
| 印花适配       | 在目标商品、底色范围和实际尺度上是否可读、协调；已知工艺要求是否满足，未知部分是否明确标注 |
| 保留对象       | 手法款：与参考是否像同一系列；意境款：盲看时是否保持目标意境                               |

借鉴参考时同时看意与形两条轴：

|        | 意或手法相似         | 意或手法不同 |
| ------ | -------------------- | ------------ |
| 形相似 | 接近复刻，不算新设计 | 失败         |
| 形不同 | 目标                 | 失败         |

可复现的检查手段：

- 盲看：不提供任务书，让评审者说出感受，与目标对照；
- 缩略：缩到列表卡片尺寸或模拟 1～2 米观看，检查识别点；
- 灰度：转灰度检查明度层级，暴露等明度撞色；
- 多底色：叠放在白、黑与目标底色上，检查主体是否消失或成为贴片。

各项分别记录通过、偏差或待验证，不用“角色很像”抵消表达失败，也不用“画面好看”抵消印制问题。

印花验收用脚本先跑一遍，不合格的再人看。检查项与初版阈值：

| 检查     | 不合格条件                                                                                             | 对应问题                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 截断     | 画布外圈 1% 范围里不透明像素超过 2%（出血裁切的那条边不算；矩形贴片不查贴片本身，改查下面两行）        | 图案碰到或越出画布边                                                           |
| 整张矩形 | 整张画布不透明超过 90%（印花形态为独立图形时）                                                         | 整张印成一块矩形                                                               |
| 贴片框外 | 矩形贴片：整张不透明超过 97%，或画布外圈 1% 内不透明超过 90%（贴片铺满画布、像直接裁出的矩形）         | 框外没有透明，边框没设计；框外的标题、徽章也出不去                             |
| 贴片边缘 | 矩形贴片：贴着实心区的半透明带，平均宽度超过 4 像素（缩到 640 像素计，干净的抗锯齿边约 1～2）           | 边框是软边、渐隐、发虚                                                         |
| 雾与光晕 | 离实心区较远、且透明度平滑的半透明像素超过前景的 5%                                                    | 整张雾、光晕；毛发与蜡笔颗粒的软边不算                                         |
| 深色衣服 | 前景里近黑（L* < 15）超过 35%；或有和任何浅色图形都不相连的深色区域（L* < 35，含深蓝字）超过画布 0.15% | 大块黑字，或直接写在透明底上的深色字（如 LEGEND、深蓝 MONDAY），在黑衣服上消失 |
| 白色衣服 | 前景里近白无彩像素超过 35%                                                                             | 白色部分在白衣服上消失                                                         |

矩形贴片的“雾与光晕”照常检查（框外不得有半透明雾）；深色衣服（孤立深色元素、近黑大面积）与白色衣服三项只记录不判定，贴片自带底色，边框与衣服色是否分得清看预览。

已知漏检：贴着浅色图形（如毛发）的深色符号会被当成与图形相连，脚本判合格；验收时同时输出黑底、白底并排预览，由人看一眼。

填充率只记录，不作合格条件：生成图普遍比原图更满，把测得的填充写进提示词只降了 0.01～0.06；上身不显拥挤即可。

**印前处理**：半透明先在生成时避免。漏网的按“改不改变观感”分两类：看不出差别的技术处理由系统自动做；会改变观感的处理是设计选择，做成用户选项，系统只给推荐（处理脚本 `printprep.py`）。

| 类别         | 处理                                                                                    | 谁决定                                     |
| ------------ | --------------------------------------------------------------------------------------- | ------------------------------------------ |
| 技术处理     | 透明度残值归一（生成图的“实心”多为 250～253、“全透明”带 1～6）；清零星杂点；保留 1～2 像素抗锯齿边 | 系统自动，肉眼看不出变化                   |
| 光晕与软边   | 保留原样、转网点、转颗粒、加底板、去掉光晕                                              | 用户选；默认按模板标注与衣服色预选推荐项   |
| 深色元素     | 深色衣服上会消失的深色字与符号加白描边，或整体加一圈贴纸边                              | 用户选；只在深色衣服上出现                 |
| 留底元素     | 外轮廓以内的透明处铺纸色（白毛、纸面、镂空字），或露衣服色                              | 数据里的留底元素决定默认，用户可改         |

选项只在检测到半透明、光晕或深色元素会消失时出现，大多数图不出现。每个选项配实时预览，铺在用户当前选的衣服色上，预览就是实际要印的文件。哪些选项开放，等实物打样后定，印不好的不放出来。

**发现与拦截的阶段**：坏的不是图本身，而是图配上某种商品与衣服色，所以生成阶段不拦。

| 阶段             | 发现什么                                       | 动作                                                                                           |
| ---------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 模板入库、拆解   | 光感是否属于意境；封面是否带整幅背景          | 给模板标印花适配：可直接印、需印前处理（深色衣服、网点化）、不适合衣服。不适合衣服的只开放杯子、海报这类不透明载体，或默认加底板 |
| 生成             | —                                              | 按标注选生成方式（深色底生成后镂空，或保留底板）                                                 |
| 生成后检查       | 雾、整块矩形、半透明占比、深色元素消失        | 做技术处理；模型自己加的雾这类意外缺陷在后台重生成一次；其余交给下一阶段                         |
| 选衣服色、下单前 | 图与所选衣服色是否合适                         | 出处理选项与预览；效果会变差的提示并推荐合适颜色；与衣服色绑死的效果（如烘焙到黑色）选到不匹配的颜色时禁选 |
| 交给工厂         | 文件里是否还有半透明                           | 硬规则：不交带半透明的文件。用户选了保留原样时，按工厂能力转换（软件能自动转网点就交原样，否则按默认网点转），并在预览里如实展示 |

提示只用于用户在预览里能亲眼看到的变化；禁止只用于印出来一定与预览不符的情况。现有下单链路（quick-design）未见半透明检查，裁边工具特意保留半透明与抗锯齿边，交给工厂前是否另有处理待与下单侧核对。

处理救不了的重新生成：雾与不透明底色混在一起，或光影本身是画面主体时，去雾后边缘会残缺。

验收脚本只回答“能不能印”，不回答“好不好看、像不像原模板”；合格之后仍要把成品与模板封面并排看一眼，意境丢了按不合格处理。

**渐变与光晕的印法**：半透明本身印不出来（DTF、DTG 会在半透明下面照样垫白墨，深色衣服上变成发白的雾和灰框），不透明的颜色渐变可以印。要保留渐变的感觉，有以下手法，效果都不如原图，按风格与衣服色选：

| 手法                 | 做法                                         | 适合                                   | 代价                                 |
| -------------------- | -------------------------------------------- | -------------------------------------- | ------------------------------------ |
| 网点（AM）           | 渐变转成大小变化的实心圆点，点间露衣服色     | 复古、波普、网点版画；丝网与 DTF 的标准做法 | 多一层印刷感                         |
| 颗粒（FM）/ 点绘     | 随机颗粒的疏密表示明暗                       | 柔光、毛发、水彩、蜡笔，最接近原貌     | 细颗粒对印刷精度要求高，粗颗粒更粗犷 |
| 线条网屏             | 平行线的粗细表示明暗                         | 版画排线、复古电视感                   | 风格化最强                           |
| 色阶分离             | 渐变分成几级不透明色带                       | 海报感；单一衣服色                     | 色带明显，只对一种衣服色成立         |
| 烘焙到衣服色         | 渐变与某一衣服色直接混成不透明               | 单色专款（只做黑 T）                   | 换衣服色就露出色块                   |
| 形状底板             | 保留原图底色，裁成圆形、拱形等实心形状       | 夜景、逆光、满幅水彩                   | 多一块底色，衣服透气感变差           |
| 镂空（与上面组合）   | 把画面里的深色底当成衣服色去掉，只印亮部     | 深色衣服上的夜光、霓虹                 | 浅色衣服上效果弱                     |

以上效果目前只在屏幕上模拟（同一张月牙图铺四种衣服色），未打样；哪几种做成正式选项，待实物打样后决定，细颗粒能否印清取决于工厂的印刷方式。屏幕上看，镂空后的细网点、粗网点、细颗粒与未处理的半透明原样最好，已送这四种打样；半透明原样是目标观感，若印厂软件能自动把半透明转成网点，可以直接交原样。镂空时光晕的不透明度按亮度反算（亮度越高越不透明，颜色还原成光本身的颜色），主体保持实心；不透明度提前饱和会把靠近主体的暗光晕印成一圈实心暗边。主体轮廓按亮度阈值硬切会带出闪粉和颗粒的毛刺，网点在原尺寸下只有几个像素也会发方；做法是先放大到 300 dpi，主体内的细缝先闭合再填洞，轮廓模糊后再取阈值，并保留 1～2 像素抗锯齿，网点一直排到主体边缘。主体阈值是按单张图调的，做成自动工序需要可靠的主体轮廓（主体单独在透明底生成，或用抠图模型）。

**不适合印花**：意境依赖大面积透明渐变（整张柔光、雾景）、又要求任何衣服色都成立的图，上面的手法都会损失主要的美感。这类图标为不适合直接做衣服印花：保留底板按矩形贴片印，限定深色衣服，或只用于海报、杯子、手机壳这类不透明载体。

出现偏差时区分三种来源：分析漏掉了重要信息；任务书转换时改变了原意或加入过度限制；模型没有执行已经明确的约束。修改描述、重新设计和局部修图解决的是不同问题，应保留这一差别。

### 反复出现的手法

1. **字图咬合**：标题字作背景层，主体遮挡部分字母，字仍可读（TROUT、SPOOKY、BEAR AND BUTTERFLY、VENOMOUS、CHEERS、STAY WEIRD）。
2. **外轮廓收形**：圆形徽章、文字绕圆、星形、爆炸框、太阳、不规则色块底，使整张图在衣身上读作一个形状。
3. **三级字层**：小标、大主标、小副标，常附一行近乎不可读的小字作纹理（FISHING／TROUT／Big Catch／Estd 1994）。这类小字的印制可行性须按工艺确认。
4. **色数克制**：单色到三色占比高；单色或双色线描（蓝、紫）呈现孔版印刷感。
5. **重复中的变化**：一排兔子、三颗草莓、头像网格。
6. **满铺涂鸦**：密集小元素填满一个形状（咖啡馆涂鸦、兔子群、床上小狗）。
7. **统一线条语言**：蜡笔、粗描边贴纸、均匀单线、丝网做旧。

### 测量参数的有效性

| 参数     | 观察                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 底的类型 | 有效。透明底样本几乎都是成品印花，矩形背景样本几乎都是插画或海报，可用于判断是否为 POD 原生设计                                       |
| 色数     | 平涂图与目测一致（樱桃 1 色，若干样本 2～3 色）；蜡笔、渐变与纹理会大幅抬高计数（目测约 5 色的蜡笔恐龙测得 63），须先平滑或做感知聚类 |
| 重心     | 区分度低。约 40 张落在中心 0.45～0.55，居中是 POD 常态而非风格参数；只有海报类明显偏离                                                |
| 明度跨度 | 能暴露肉眼易忽略的问题，如 NO WAR 的蓝与红几乎等明度                                                                                  |
| 前景占比 | 按整张画布计算会混入画布边距，只能粗分饱满与疏朗（约 0.6 与约 0.13）；比较设计疏密改用内容框内填充率                                  |

字图咬合、外轮廓收形、字层和风格类型无法通过像素统计得到，需要读图描述。

### 暴露的适配问题

- 白色主体（郁金香兔子）印在白色衣身上会消失；
- 黑色矩形底（骷髅熊）在浅色衣身上成为黑框；
- 等明度撞色（NO WAR）在灰度或单色印制时红叉消失；
- 第三方 IP 角色、10 号球衣球员及图库水印素材只能参考手法，不能作为素材。

按 writing-for-agents 的原则重写编译写法（开头明确指令、内容在前参考在后、每样东西只写一处、正向描述），同一份数据两种写法各出四张：画面几乎一样，没有退步；字数少约 10%，否定从 10～20 处降到 2～6 处；颜色绑定更准（“困死了”的小英文按指定画成淡紫，旧写法画成灰蓝）。采用新写法作为默认。

配色只在生成时约束，后处理换色已否决：原型在八种画法上没有出现边缘或纹理瑕疵，但会把物件本色一起换掉（咖啡变绿）、调亮后颜色变名（朱红变粉）、文字对比度下降，效果不如重新生成。随后把颜色写成“中等深浅的松石绿”这类带档位的名称，或附上色值：拉面与唱片的主色明度从 27 回到 36～51，整体平均明度 60～72（原图 62）；色值略稳，但两种写法误差都在 ±10 以内。拉面的珊瑚橙仍偏艳。

按问题清单修订编译脚本与文档后：颜色改用占位引用，没有文字的设计、附图说明、姿态、用户指定内容、主体固有色都有了明确字段与写法；新增测量与印花验收脚本，验收脚本对已知的坏图（截断、矩形贴片、晕边、半透明底）全部判为不合格。满铺涂鸦的物件尺度改用“以原图为编辑底图逐件替换”后保住，但新文字长度与原文差得多时会写错。

在五个新模板上复测修订后的方法：同款类三个里，“我是一片吐司”和“皇冠涂鸦纪念卡”拆解法明显更接近原模板（模板配方附了原图，仍丢掉了吐司脸、改掉了版面），“尖叫星星”持平；风格配方的吉祥物拆解法手法更像；画风重绘的稚线蜡笔，模板配方画风更像，但在透明底下变成整张半透明雾，拆解法才能直接印。据此补了标志特征默认保留、用户输入不跨画法大类、套色模板随配色、出血裁切与画幅默认等规则，并修正了验收脚本对雾、黑字与近黑的判断。

再测五个此前未用过的同款场景配方模板（拆解法附原图并写明颜色）：牛角包里藏着猫、打哈欠的早安晨报两个拆解法明显更接近原模板，鼻涕都流了还在加载略近，怒火烧到头顶了持平，我也是一只饺子各有所长（模板配方的“蜷成食物形状”更到位，拆解法的线条与视角更像）。加上前一轮，八个同款场景配方模板里，附原图并写明颜色的拆解法没有一个不如模板配方。核心特征默认保留、同款档保留矩形海报、点缀色写色值三条生效；线条深浅只部分生效（深浅对上，线条偏细偏少）。

补测出血裁切：两个底边被切开的胸像模板（复古宠物时装肖像、蓝调网点肖像），附原图时把形态从“出血裁切”改成“完整落在画布内”，八张仍全部切开，只改一句形态压不过原图。随后改用收形元素，每种收法各出两张：底托、容器、渐隐、自然收形、形状蒙版、异形裁切、笔刷遮罩在两个模板上都画出来了，只有网点款的笔刷遮罩和一张拱窗偏弱。底托、容器、拱窗、撕纸边的边缘是实心的；照片款的渐隐、毛衣下摆和笔刷边画成了半透明，验收判为雾。网点款在深色衣服上看不见，与收法无关：原图的白色在透明底下变成透明或半透明，硬切对照组也一样。

半透明处理：用已有生成图试印前工序，深色字加白描边后在黑衣服上可见（贴着彩色字的深灰字会漏判，要整体描边），渐隐转网点或颗粒后仍是渐隐且能印，网点款铺纸色后在黑衣服上恢复白底，整片雾能清掉。再拿两个容易出光晕的新模板（月牙上的施法时刻、接住这条逆光游来的锦鲤）比旧写法与实心写法：附原图时两种写法都把夜空或水彩底画成整块矩形，比不出差别；锦鲤改为不附原图后，实心写法画出实心放射光芒、实心鳍和实心气泡，两张生成即合格；月牙附去掉夜空的原图后不再是矩形，但抠图留下的软边把光晕带了回来（雾 0.11～0.20），去雾后合格，月牙内弧边缘略残。两组“合格”的成品都难看：锦鲤的水彩柔光变成尖刺放射，月牙的柔光被切掉、边缘发灰，意境丢了。改用深色夜空版生成图离线试印法：底色镂空后光晕转成颗粒或网点，黑色、藏青衣服上接近原图；据此改为先判断光感是否属于意境再分流，并整理渐变与光晕的印法。

## 当前验证边界

- 夜班快递员的两种方向显示：表达意图可以带来不同构图；尚不能据单次结果证明约束具有稳定泛化能力。
- IP 试验显示身份可以延续到新动作；同时出现安静版人物过大、速度版轮廓截断等偏差，需要分别验收身份和美学。
- 分格方案曾通过局部编辑修正裁切错误；这不能计作纯文字一次生成成功。
- 渐变与光晕的印法（网点、颗粒、点绘、线条网屏、色阶分离、烘焙到衣服色、形状底板、镂空）只有屏幕模拟，待实物打样验证后再定正式选项；印前脚本尚未实现镂空。
- 胸前小图、前胸主图和后背大图的实际尺度对比、服装上身效果与工艺打样尚未完成，不能标为 POD 适配已通过。
- 手法迁移只在一张参考（TROUT）、两个题材上做过两轮，初步成立；尚需更多手法类型（复古徽章、满铺涂鸦、童趣手绘）与盲看评审，以及上身与打样验证。
- 意境迁移尚未验证：需为参考写出意境与承重关系，生成多张形不同的候选，以盲看判断意境是否保持。
- 拆解信息是否足以理解原图尚未系统验证：可将拆解结果交给看不到原图的评审者，让其复述画面并回答层次、轻重、配色等问题，按原图评分。
- 参数提取的稳定性尚未验证：同一张图多次提取时，可描述类字段的一致程度，以及参数转回图像后再提取的偏差，都还没有数据。
- “做同款”的默认档位尚未验证：需按“标志特征与复刻刻度”中的两题盲测，分别测认出与偏好。
- 待验证重点是：在不同题材、IP 与商品条件下，关系约束能否继续指导有效的新布局，而不是只复现某张参考图。

- 生效日期：2026-08-26
- 对象：负责从模板参考图分析并输出批量导入 JSON 的运营同学 / Agent
- 目标：高保真保存模板制作人的意图，并明确 JSON → MySQL → Prompt Compiler → 生图模型的数据链

本文的参考图、提示词占位符、风格锁定及 `runtimeSemantics` 要求适用于普通提示词编译链路。
`kind=SKILL` 的 C 类模板走已登记能力合同：`remoteRunKind` 必须在代码目录存在，输入槽必须匹配

能力允许的配色、构图和质感选项可直接开放，详见 [`skill-authoring.md`](./skill-authoring.md)。

## 最终结论

Agent 生成的新模板要进入 v2 链路，运行时最小权威由四部分组成：

1. `referenceImage`：模板视觉参考图。
2. `promptTemplate`：带输入占位符的基础画面内容。
3. `inputSchema`：用户可以提供哪些内容或身份输入。
4. `runtimeSemantics`：输入接管哪个成图位置，以及必须保持的媒介、画风、构图和关系。

其中 `runtimeSemantics` 不能删。只存参考图、提示词和输入槽，会丢掉“谁替换谁、上传身份不能扩散到哪里、哪些关系必须保留”等关键信息。

新的 v2 模板不应再让 Agent 手工维护 `promptEnhancement`。当前 v2 worker 使用 `runtimeSemantics` 做一次性 Prompt Compilation，不消费 `promptEnhancement`；后者只用于无 `runtimeSemantics` 的 v1 任务兼容。若回滚兼容仍要求保留，应由 Import Adapter 从 `runtimeSemantics.visualContract` 单向生成，不能成为第二份作者权威。

`metadata` 可以继续保存分析理由、候选建议和审计信息，但它永远不参与生成。任何必须影响成图的内容都必须进入上述四项，不能只写在 `metadata`。

### 图片模式：不要再写 `image.extract`

`inputSchema.version` 固定为 `2`。每个 `slots[]` 槽位可独立声明 `text`、`image` 或二者兼有；“人物”“背景”“装饰”来自 binding 语义，不来自输入类型名。`image` 只负责图片模式的上传与资产约束。`image.extract` 不属于当前合同；它是存量模板里可能残留的旧字段，导入或重新解析时不会进入运行链，也不会影响最终提示词。

运营看到旧 `extract` 时，先判断它真正想表达什么，再迁入唯一的执行权威：

| 旧文案真正表达的意图                             | v2 写入位置                                                              |
| ------------------------------------------------ | ------------------------------------------------------------------------ |
| 上传图提供哪个身份、接管哪个画面位置             | `runtimeSemantics.inputBindings` 的 `replace_identity` 与 `targetIds`    |
| 按模板媒介重绘，并保持画风、构图、接触或遮挡关系 | `renderingMode: "illustration_redraw"` 与 `visualContract`               |
| 先读取图片并产出文字或 JSON，再把结果写进提示词  | 显式 `preprocessSteps` `vision` 步，并在 `promptTemplate` 中引用步骤输出 |

不要把旧 `extract` 原句整段复制进 `visualContract`。先删除平台通用套话，只保留这个模板独有且必须跨用户改写保持的媒介、画风、构图和关系。若确实配置 `vision` 步，还要确认其输出被 `promptTemplate` 引用；被 vision 消费的图片只用于提取，不再作为原图直通生图模型，因此“读图转文字”和“图片身份直通”是两种不同方案。

完成标准：新 JSON 中不存在 `image.extract`；旧字段里的每条有效意图已经归入 binding、visual contract 或一条有输出引用的 vision 步，通用套话和无消费方内容已删除。

### 运营如何决定一个槽支持文本、图片还是二者

槽位名称描述稳定的用户意图，不描述模板的默认答案。例如，一个允许用户上传室内、自然、街景或舞台图片的槽应叫“环境”或“背景”，不能因为默认画面是城市就叫“城市背景”。“城市街区”属于 `text.defaultValue` 或文本建议值。

文本和图片是两个正交模式：

- 只需一句描述就能稳定表达的输入使用 `text`，例如天气、色调、服装款式、装饰文案。
- 上传图有明确、稳定的成图接管区域时使用 `image`，例如人物身份、完整环境、明确道具。
- 同一意图既适合文字描述又适合上传参考图时同时声明 `text + image + image_over_text`。图片模式激活后，本次运行只采用 `image.promptValue`，不得继续混入 `text.defaultValue`。

不要求每个槽都支持图片，也不设置“至少一半槽位可上传”之类的机械比例。判断标准只有一个：上传图是否有明确接管目标，并且当前执行链能稳定完成对应 binding。为了凑比例给天气、色调或零散服装细节增加图片模式，会让运营界面看似可上传，实际生成时没有清晰的替换边界。

人物图片默认提供人物可见身份特征，包括外貌、发型、服装和配饰的大致整体印象。若模板另设“外套”“围巾”等文本槽，显式输入可覆盖这些已声明区域；合同不承诺把人物图精确拆成无限细的服装部件。运营只需让用户理解“人物图决定整体人物，单独填写的特征决定对应局部”，不需要描述模型无法保证的像素级边界。

环境图片模式的通用写法是：

- `image.promptValue` 描述采用上传图中的完整环境、主要内容和空间布局，不写默认地点。
- binding 使用 `replace_content` 指向一个明确的 `content_element` 环境目标。
- `visualContract` 可以保持模板媒介、人物位置、空间层次、时间或天气转译，但不能把可替换的默认建筑、道路、室内陈设等继续写成必须保留项。

### 同时含身份图与内容图时的来源隔离

本段只适用于同一模板同时声明 `replace_identity` 与 `replace_content` 图片模式的情况，不要求纯身份替换、纯内容替换或只有文本输入的模板增加无关约束。

- `targetInstances[].role` 描述目标在成图中的稳定职责，例如“人物所在的完整环境”，不能写成“雪山湖面”这类默认答案；默认内容仍归 `promptTemplate`。
- 身份图只为绑定的 `identity_subject` 或 `identity_group` 提供身份。若其原图背景、构图、色彩或光影不应进入内容目标，必须在 `visualContract.relations` 明确排除。
- 当内容图以 `replace_as_unit` 接管完整 `content_element` 时，必须在 `visualContract.relations` 明确：本次激活的内容输入是该目标唯一视觉内容来源，不从身份图背景或模板默认内容补取题材。
- 作者 JSON 只声明“输入槽 → 目标”的语义关系，不把固定的“图一”“图二”当作来源身份。运行时根据模板参考图和本次激活输入的实际顺序动态编号，并在发送模型前说明每张图的角色。

完成标准：即使身份图带有醒目且无关的背景，内容图又是完全不同的题材，制作人和运行时仍能唯一判断每个目标由哪个输入接管，不存在两个来源同时争夺同一内容目标。

### 逐图说明同时保留字段职责与必要的实际画面内容

作者 JSON 不得预写“图二是金发少女、图三是汽车”这类未来上传图的固定答案。v2 运行时会在生图前对本次实际直通图片做一次合并视觉摘要，并把最终图片顺序写成简短的逐图说明：

- 模板参考图用 `visualContract.medium` 做一句画面概括；构图由参考图本身与已审计合同承接，不在角色段重复展开。
- `replace_identity` 图片只声明“这是哪个字段的身份图、接管哪些人物目标”。精确身份由原始图片像素决定；不得再把人脸翻译成“黑发、齐刘海、蓝眼”等二手外貌标签后发给图片模型，否则会把“这个人”降级成“这类长相”。视觉摘要仍可留在内部 trace 和诊断报告中。
- `replace_content` 图片概括完整场景的主要物体、媒介和关键空间关系，场景中的人物也属于内容描述。
- 每条说明同时保留运行时图号与 `inputId`，例如“图 2（subject）”，再说明它只接管哪个目标。

内容图的视觉摘要只帮助图片模型区分“每张图里有什么”，不是新的 binding 权威，也不能改变 `targetBindings`。服务端按图片序号而不是模型回写的字段名绑定摘要；缺项、重号或视觉调用失败时，整组摘要作废并降级为只有字段和目标的逐图说明，不能猜测或错绑。内部 `sourceId` 不进入最终提示词，它用于校验来源声明，不帮助图片模型理解画面。

### 默认字段不是编辑动作

当模板参考图存在，且某个标量内容字段的当前值等于 `promptTemplate` 或输入合同声明的作者默认值时，参考图已经承载该可见内容。运行时仍要把字段、当前值和默认值命中记录在任务快照与审计账本中，但不得再把它伪装成一次 `replace_content` 发给图片模型；重复要求模型“删除原字，再写回完全相同的字”既增加提示词噪声，也更容易破坏文字和身份替换。

只有当前值真实偏离作者默认值，或本次没有模板参考图可承接默认画面时，标量字段才编译成显式内容替换。这个判断来自模板版本与本次执行值的确定性比较，不由 LLM 2 猜测，也不按具体字段名穷举。

### 编辑后容器依赖：先判关系，再编译动作

当内容目标 B 的可见区域由另一个目标 A 的形状定义，并且 A 会被本次输入完整重绘时，B 必须使用 A **编辑完成后的新几何**作为裁切边界，而不是模板参考图中 A 的旧几何。这叫 `post_edit` 容器依赖；人物剪影只是其中一个实例，同一规则也适用于宠物外形、服装轮廓、商品外形或其他会随输入改变的封闭形状。

作者仍只维护一份 `runtimeSemantics` 权威，不手写编译器的解释结果。要让运行时有足够证据判断关系：

- A 与 B 分别建成明确的 `targetInstances`；A 的 `role / region` 描述会变化的容器形状，B 的 `role / region` 描述位于该形状封闭实体区域内的内容。
- A 的激活 binding 使用 `replace_identity + illustration_redraw`，B 的激活 binding 使用 `replace_content`。
- `visualContract.relations` 正向声明“B 按当前 A 的轮廓裁切，A 外保持哪个模板层”，不要只写“保持原图”或预设固定图号。

作者合同必须让每个激活的 `replace_content` 目标都能从 target 类型与原子 `relations` 唯一判断以下关系。
默认 Compact Renderer 直接按冻结关系编译，不再让模型补猜；Seven 线上回退会保留原可审计分类，
但它不是作者数据缺项的修复机制：

| 分类             | 判定                                                   | 编译口径                                                |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------- |
| `post_edit`      | B 位于本次会重绘的 A 的封闭轮廓内                      | 先完成 A 的新几何，再以新几何裁切 B；明确排除模板旧轮廓 |
| `template_fixed` | B 位于不会被本次输入改变的字母、相框、面板或固定容器内 | 继续使用模板固定边界                                    |
| `independent`    | B 是普通背景、环境、道具或独立区域                     | 按自己的目标替换，不写成 A 的剪影填充                   |

不要因为同一模板同时有身份图和内容图就机械判定 `post_edit`。接触、遮挡、前后层次不是容器关系。以下案例只用于校准判定，不是规则本身：

- 新人物轮廓内填入场景、新宠物外形内填入纹理：`post_edit`。
- 固定 `LOVE` 字母内填入照片、固定相框内换图：`template_fixed`。
- 人物后方替换街景、人物旁边替换道具：`independent`。

这套解释解决的是语义依赖，不会把单轮 `image.edit` 变成像素级 mask。Prompt Compiler 会要求内容只进入新轮廓的封闭实体区域，间隙、孔洞、轮廓开口和目标外保持模板原层；但模型仍可能出现边缘扩散、形状漂移或固定层被覆盖。

如果模板验收要求逐像素稳定，应保持 `DRAFT`，改用能生成并传递显式 mask 的 Skill / 两阶段执行能力后再发布。固定使用模板旧轮廓的 mask 不能替代该能力，因为它会把本应随输入变化的新外形锁回模板几何。验收时必须分别判断“内容来源正确”和“内容边界正确”；三次试跑中任一次出现目标外扩散，都不能把模板记为通过。

### 约束账本：每条作者意图都必须有去向

Prompt Compilation 先用较快的视觉模型最多一次识别实际送给生图模型的模板参考图与全部用户图，只产出逐图可见事实；随后默认由服务端确定性 Compact Renderer 输出 `compact_vocab_v1`。v1/v2 合同、精确文字、用户改写、内容图片、多来源、reference-only、宠物组和 `preserve_pixels` 都使用同一套固定词汇编译。原 `seven_section_v1` 与第二次 LLM 作为线上质量冷备保留，只能由系统配置中心显式切换，不能由模板作者或单次请求选择。

完整账本与任务 binding 是**审计权威**，图片事实模型不产生新绑定。默认 Renderer 用 `组映 / 同像多映 / 身份净替 / 像素映 / 内容替 / 文字替 / 参考 / 用户改 / 风格译 / 模板锁 / 动作锁 / 模板字锁 / 来源隔离` 编译执行语义，并把内部 id 投影成 `图N` 与可见目标角色。600 字符是常规任务目标；若复杂多编辑任务不能在不截断精确内容的前提下压到 600，保留完整内容并留超目标观测。Provider 只收到当前模式的最终 Prompt 与实际图片，不收到内部资产标识。

`same_source_repeated` 同样按语义编译：若绑定覆盖模板全部身份目标，执行词写“模板图全部 N 个人物”；若只覆盖子集，才列出具体角色。身份与原姿态发生冲突时身份来源优先，避免“保留表情”把模板原脸一起保留下来。这些都是 policy 分支，不是针对某张图的 few-shot 或字段名特例。

这意味着 `preservedDimensions: ["styleTraits"]` 之类维度标签不能代替实际画风条目。修复人数时，画风、构图、固定内容和关系仍各自保留独立账本项；Renderer 会按固定优先级压缩重复散文，但不会用模型计划删除作者事实。

如果存量 `medium / styleTraits / composition / colorAndLight` requirement 把可替换目标的旧默认答案与结构约束写在同一句里，默认 Renderer 只能按冻结结构与激活 binding 处理，不能把 Seven 回退中的第二次 LLM 当作长期猜测 `structuralOnly` 的依赖。新模板必须从作者数据中移除可替换默认答案，并把结构、默认内容和来源归属拆成原子条目。

作者不需要新增字段，但每个数组项应保持**原子、正向、可执行**：一项只表达一个必须同时成立的视觉事实；不同优先级或不同区域的要求拆成多项。完成标准：删除任意一条 `styleTraits / composition / relations / colorAndLight` 都会真实改变验收口径，而不是与相邻条目重复或只写“保持风格”这类无可观察结果的标签。

## 制作流程

1. **建模参考图。** 识别每个开放输入要接管的可见位置，以及必须防止身份误占的关键内容位置。完成标准：每个位置都能写成明确的 `role + region`，且没有用“主体”“元素”这类无法区分实例的泛称代替。
2. **编写三份互相引用的运行数据。** `promptTemplate` 写基础画面，`inputSchema` 写用户能改什么，`runtimeSemantics` 写输入如何接管及必须保持的视觉合同。完成标准：每个文本槽都被提示词引用、每个直通图片模式都有唯一可执行 binding、每个 binding 都指向存在且类型匹配的 target。
3. **分配身份并通过真实校验器。** 能维护稳定 ID 时，我方原生新模板先运行 `pnpm gallery:template:id`，外部长期维护的数据携带自己的 `sourceIdentity: { source, id }`。运营当前只有 key 时可省略两者，导入器按唯一 key 回退；key 改名无法保持身份，多候选会失败并要求补内部 ID。再运行 `pnpm gallery:validate <file-or-dir>`。后台批量导入时由调用方包装成 v4 bundle。完成标准：结构和交叉引用均为零 error，warn 已逐条判断并处理或记录理由。
4. **建议先试跑，也允许直接上架。** 新模板以 `DRAFT` 导入，建议至少使用三组不同输入检查身份位置、构图、媒介和关系；平台把证据不足显示为质量提醒，不作为状态硬门禁。动态群像的三组输入应覆盖不同成员数，并检查每位成员都参与作者声明的共同关系。同时含身份图与内容图时，其中一组应使用“身份图带醒目背景、内容图为明显不同题材”的对抗输入。若选择试跑，完成标准是三组结果都满足 visual contract，且对抗输入的内容目标只采用内容输入、不挪用身份图背景。任何成员缺失、重复，或未参与“共同托举 / 相拥 / 围拢”等核心关系，都是画面质量失败；修改 JSON 说明、metadata 或人工备注不能把失败结果计作成功证据。

运行链、数据库字段血缘和 Prompt Compiler 内部实现属于工程分支，按需读取 [`runtime-prompt-context-design.md`](./runtime-prompt-context-design.md)；制作模板不需要复述这些实现细节。

## Agent 批量输出格式

Agent/CLI 同时接受“一模板一 JSON 文件”和 `{ "version": 4, "templates": [...] }` bundle。目录模式仍适合逐图配套的批量产出：

```bash
pnpm gallery:validate <模板目录>
pnpm gallery:import <模板目录> --dry-run
```

单模板文件顶层可以是 `id/key/title/promptTemplate/...`、外部维护数据的 `sourceIdentity/key/...`，或运营旧格式的 `key/title/...`。我方 `id` 仍是内部跨环境稳定身份；历史模板做过归并时，旧 `id` 会先经内部别名解析到主模板；`sourceIdentity` 是外部 `(source, id)` 到我方 ID 的持久别名；两者都缺失时仅在同 key 候选不超过一条时回退。bundle 顶层的 `version: 4` 是导入包协议版本；每条模板内部的 `inputSchema.version` 固定为 `2`，新写入的 `runtimeSemantics.version` 固定为 `3`，三者独立版本化。运行时仍可读取 `runtimeSemantics.version: 1/2` 的历史模板，但新作者数据不得继续写 v1/v2。版本升级与兼容承诺见下方 [版本与兼容规则](#版本与兼容规则)。校验与 dry-run 都会逐条报告 bundle 中的问题。

后台作者录入页若发现文件显式 `id` 尚不存在、但当前环境已有同 key 模板，会暂停并要求运营明确选择
覆盖、新建或本次跳过；它不会静默把 key 当主键。选择只对本次录入生效，不会创建 ID 别名或绑定
`sourceIdentity`。CLI 仍按显式 ID 严格执行。作者侧要避免反复出现这道选择，应从当前环境导出并保留
真实 `id`，或通过独立身份流程维护稳定 `sourceIdentity`。

外部身份示例：

```json
{
  "sourceIdentity": {
    "source": "partner-a",
    "id": "local-template-42"
  },
  "key": "readable-key",
  "title": "模板标题"
}
```

`source` 由接入方固定，外部 `id` 只需在该 source 内稳定唯一。没有外部 ID 时可直接省略整个 `sourceIdentity`，使用现有 `key`；唯一候选自动更新，无候选确定性新建，多候选失败并要求补目标内部 `id`。完整边界见 [`template-import/README.md` 的“三档导入身份”](./template-import/README.md#三档导入身份)。

### 导入身份不等于创建者身份

`id`、`sourceIdentity` 和 `key` 只回答“这次导入应更新哪份模板”，都不声明“模板属于哪个平台用户”。运营 / Agent JSON 不得新增顶层 `authorId` 或 `creatorId`：后台创建与运营导入统一归属平台运营；用户创作者身份只能由已登录投稿链路在作品通过发布门禁后由服务端绑定。`metadata.author` 可以记录素材署名或分析来源，但不是账号身份，也不得参与导入匹配。

已经通过真实校验器的固定身份样例见 [`template-import/agent-v2-example.json`](./template-import/agent-v2-example.json)，动态合照群组样例见 [`template-import/agent-v2-dynamic-group-example.json`](./template-import/agent-v2-dynamic-group-example.json)。

## 版本与兼容规则

三条版本轴各自独立演进。作者只需要记住一条：**永远按本文当前口径写，不写任何旧版本号**。兼容旧数据是导入器和运行时的职责，不是作者的职责。

| 版本轴                          | 当前值 | 作者怎么写                        | 旧版本的命运                            |
| ------------------------------- | ------ | --------------------------------- | --------------------------------------- |
| 导入包 `version`（bundle 顶层） | `4`    | bundle 写 `4`；一模板一文件不涉及 | v3 继续可读；v1/v2 先用身份升级工具升级 |
| `inputSchema.version`           | `2`    | 固定写 `2`                        | v1 数组形态读时适配、写库时归一成 v2    |
| `runtimeSemantics.version`      | `3`    | 固定写 `3`                        | v1/v2 原样兼容；新模板不得伪装旧合同    |

**兼容承诺**——「规范迭代之后旧模板仍然能用」靠以下四条机制保证，不靠作者自觉：

1. **读侧永不丢版本**：库里存在过的每个版本，导入器与运行时保持可读，直到回填把该版本清零并审计确认才允许移除。已发任务与已生成作品读的是钉住的模板版本快照（`GalleryTemplateVersion`），规范升级不会改变它们的行为。
2. **写侧只有当前版**：新产出一律写当前版本号。导入器对能无损归一的旧形态（如 v1 `inputSchema`）在写库时统一升级；不能无损表达的（如 v1/v2 `runtimeSemantics`）保留原样只读，不做有损翻译。
3. **未知版本响亮拒收**：版本号比当前导入器新 → 整包拒绝并报出版本号，绝不「尽力而为」解析——静默误读比失败响亮更危险。拿到这个报错说明产出方比消费方新：先升级部署再导，**不要改小 JSON 里的版本号硬塞**。
4. **同版本加可选字段不升版本**：新增可选键遵循「不带这个键 = 旧行为不变」。v3 引入内部 `id`，v4 增加 `sourceIdentity` 并允许运营 key-only 兼容输入；v1/v2 bundle 仍必须先用 `pnpm gallery:template:upgrade-identity` 升级，不能只改小版本号绕过包结构升级。

运营可指定可选布尔字段 `isFeaturedStyle` 来精选部分风格模板，并用现有 `sortOrder` 指定展示顺序。
Agent 只传递运营指定的选择，不自行挑选或默认把全部风格设为精选。省略字段保留目标库原值，
新建默认 `false`；显式 `false` 取消精选。`true` 必须声明 `kind: "STYLE_REF"`，且模板不能归属 Maker。
这两个字段属于运营展示配置，不进入提示词、运行语义或模板内容版本指纹。

**例外：拆解数据模板。** 只有导入了拆解数据（印花同款的 `designSpec`）的模板写运行语义 v4，见下节；其余模板仍固定写 `3`，`CURRENT` 不变。

什么样的改动才升版本号：字段语义或形状变化、删除字段、可选转必填、占位符语法变化——凡是旧读者会**误读**（而不只是「读不到新能力」）的改动。工程侧的升版本操作清单见 [`template-import/README.md` 的「版本与兼容性（工程侧）」](./template-import/README.md#版本与兼容性工程侧)。

## v3：目标外观与姿势分开归属

`targetInstances` 的三种目标都可声明 `appearance: string[]` 与 `pose: string[]`，各最多 40 条、每条最多 500 字。没有该类事实时可省略；已有事实必须完整保留。

- `appearance` 描述该目标原有的物种、体型、颜色、五官、发型等外观。该目标被本次激活的身份或内容编辑接管时，编译器移除这些旧外观约束。
- `pose` 描述姿势、手势、朝向与位置，用不含旧物种/外貌的谓语，如“右手举勺、踮脚”。替换后绑定到新主体；未替换时与外观一起保留。
- `visualContract` 只放主体无关的媒介、画风、色光、构图及跨目标关系；不得把“水滴状的透明身体”这样的具体外观留在全局锁中。媒介必填，分离后没有全局事实的数组允许为空。服装归属继续遵守 `clothingOwnership`，明确的模板服装锁定不得随外观误删。
- `role` 是目标的中性称呼（如“主角”），`region` 描述位置，不拿它们储存物种或外貌事实。
- 默认值、未激活输入与仅作参考的图片不构成目标替换。正式事实在 compact、natural、tags 中保留全文，超预算记 `overTarget`；图片辅助描述仍可压缩。

```json
{
  "id": "main_subject",
  "kind": "identity_subject",
  "role": "主角",
  "region": "画面中央",
  "appearance": ["水滴状透明身体，圆眼睛"],
  "pose": ["右手举勺，左脚踮起"]
}
```

新作者及远端模板编译产物直接写 v3；不能只把旧 JSON 的版本号改成 3。存量模板使用后台“视觉事实归属”：模型只建议已有原文的归属，无法判断的条目标记待确认；人工逐条核对、编辑或拆分后，确认完整事实再应用为新模板版本。可丢弃草稿。来源版本或合同变化会拒绝采用，必须重做审核；历史版本与已发任务快照不改写。不把旧模板批量自动改成 v3，也不从图片推测回填缺失事实。

## 运行语义 v4（拆解数据）：第 3 阶段开发完成（生成链路已接入，待 UAT 对比），生产开关默认关

> 规格正本是 [`print-design-semantics-v4-spec.md`](./print-design-semantics-v4-spec.md)，方法正本是 [`print-design-preparation.md`](./print-design-preparation.md)。
> 当前实现到第 3 阶段（开发完成）：第 1 阶段（Schema 与入库）使 v4 模板可以导入、导出、就绪检查、跨环境发布和后台只读展示，第 2 阶段补上确定性编译器（`generation/compile/design-spec-compiler/`）与导入时的编译器检查，第 3 阶段把编译器接进生成链路。**生成仍由引擎开关 `GALLERY_PROMPT_DESIGN_SPEC_ENABLED` 控制（默认关）**；UAT 对比验收尚未做，在此之前不要在生产打开。

v4 保留 v3 的绑定权威，视觉权威由 `designSpec` 承担：

| 字段              | v4 写法                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------- |
| `version`         | `4`                                                                                          |
| `targetInstances` | 形状同 v3；每个 `id` 必须是 `designSpec.elements[].id` 或 `designSpec.whole.colorRoles[].id` |
| `inputBindings`   | 形状同 v3；`replace_content` 必须声明 `valueKind`，并新增 `color`（配色输入，只在 v4 允许）  |
| `visualContract`  | **不得出现**（写了即拒绝）                                                                   |
| `designSpec`      | 拆解数据，字段见下                                                                           |

绑定与元素的对应规则（导入校验强制）：

- `replace_identity` 只绑定主体元素（`category: "subject"`）。
- `replace_content` + `valueKind: "exact_text"` 只绑定文字元素（`text`）。
- `replace_content` + `valueKind: "scene_description"` 绑定主体、点缀（`accent`）或装饰（`decoration`）元素。
- `replace_content` + `valueKind: "color"` 只绑定配色角色（`designSpec.whole.colorRoles[].id`）；目标实例 `kind` 写 `content_element`。
- 每个 `targetInstances[].id` 在 `designSpec` 里都要有同名元素或配色角色；没有被输入接管的元素不需要目标。

`designSpec` 字段（英文 camelCase，括号内为方法正本的中文名）：

- `tier`（档位）：`same_method | signature | same_design`。只有 `same_design` 生成时附模板原图。
- `whole`（整体层）：`tone`（调性）、`technique`（画法）、`composition`（构图骨架：`canvas`、`balance`、`types`、`layout` 版面 JSON、`relations`、`layers`、`visualWeight`、`density`）、`printForm`（印花形态：`standalone | rect_patch | bleed_crop`）、`crop`（裁切）、`mechanism`（表达机制）、`paletteSummary`（配色总述）、`colorRoles`（配色角色：`id`、`name`、`usage`、`appliesTo`、`belongsToTechnique`）、`prePress`（印前）、`omitTemplateImage`（可选；封面带整幅背景或光晕、又要做独立图形时标 `true`，同款档也不附模板原图）。
- `elements`（元素层）：按 `category` 区分 `subject`（主体：`originalObject`、`shapeFeatures`、`genericShape`、`inherentColorPolicy: keep | follow_palette`、`pose`）、`accent`（点缀）、`decoration`（装饰）、`text`（文字：`role`、`letterform`，可选 `followsSubject: true`）、`edge`（收形）；共有 `id`、`purpose`（作用）、`instance`（实例，只作证据）。
- `signatureFeatures`（标志特征）、`lockedInstances`（锁定实例）、`bannedWords`（禁用词）。
- `printFit`（印花适配）：`verdict: direct | needs_prep | not_for_apparel`、`lightIsMood`、`recommendedMethod`。
- `defaults`（作者默认迁移条目）：`subject`、`subjectName`、`texts`、`specifiedContent`、`accentSources`、`colors`（键为配色角色 `id`）等，即用户什么都不填时的取值。

**文字跟随主体（`followsSubject`）**：文字元素的内容是“关于主体的”（词典页的词头、音标、释义，人物卡的名字）时标 `followsSubject: true`，只能写在 `category: text` 元素上（写在其他类别导入即拒绝）。用户换了主体（文字或照片）却没填这一处文字时，编译器不写默认字，改写成“按新主体来写”（只约束角色与字形，具体词由模型按新主体写），版面 JSON 里的文字也换成占位描述，旧主体的词不会留在提示词里；用户填了就逐字照写；没换主体时默认字照旧逐字照写。没标的文字（品牌词、固定口号）无论换不换主体都保留默认字。

**单一权威**：v4 模板的 `promptTemplate` 只作展示与检索，由 `defaults` 单向生成（项目 Skill `print-same-style` 的 `scripts/to_v4.py` 已实现），不再由作者手写，编译器也不读取它。需要修改拆解数据时导出 JSON、改 `designSpec` 后重新导入；后台运行语义编辑器对 v4 只读。

**引擎开关**：系统配置 `GALLERY_PROMPT_DESIGN_SPEC_ENABLED`（默认关）。关闭时 v4 模板在就绪检查中为“未启用”（阻断），对齐入口与编译入口都拒绝处理（已排队的 v4 任务在开关关闭后也不再编译）；开启后就绪检查放行、生成走 v4 编译器。导入校验（含就绪检查）除结构与对应关系外，还运行编译器检查，不合格的 v4 数据直接拒绝：原物词、抽象风格词、会画成半透明的词、未知颜色占位 `{色:角色名}`、固有色策略为“保留”却给主体配色、矩形贴片没有收形元素；报错文案与 `compile.py` 一致，检查对象是 `designSpec` 与 `defaults`。作者写 `{色:角色名}` 时角色名必须是 `colorRoles[].name`。版面元素的键序固定为 id、role、text、content、shape、region、bbox、z；bbox 数字按 JS 规则输出（写 `1.0` 会输出 `1`）。

**生成时的行为（第 3 阶段）**：

- 编译器在 Runtime Compiler 接缝内按冻结合同的 `version === 4` 选用；不调用图片事实模型（LLM 1）、不进 compact / seven_section，也不受全局 `GALLERY_PROMPT_COMPILER_MODE` 影响；冻结上下文与载荷版本不变（`RuntimePromptContext v2`、`AlignedPayload v3`）。
- 用户输入到迁移条目的映射见规格第 4 节，每次由冻结的 `activeInputValues` 与 `inputBindings` 确定性推出。上传的主体照片写成“图片中的主体”。
- 参考图：`same_design` 且未标 `omitTemplateImage` 时附模板原图；有主体照片时原图为图 1、主体照片为图 2，附图说明由运行时生成，作者数据不写图号。v4 只支持一张主体照片，其余图片输入（内容图、纯参考图）在编译时拒绝。做同款的参考图固定取模板原图，不用来源作品图。
- 背景由印花形态与印花适配决定，用户的“透明版”开关在 v4 模板上隐藏，提交值不采用：`rect_patch`（设计贴片）→ 请求透明底（画布透明，贴片本身不透明，与 `lightIsMood` 无关，光感留在贴片内）；`standalone` 且 `printFit.lightIsMood` 为 false → 请求透明底；`standalone` 且光感属于意境（深色底生成）、`bleed_crop` → 不透明。`rect_patch` 必须带至少一个 `edge`（收形）元素描述贴片的设计边框（包边、撕边、齿边、圆角、票根、相框等），否则导入检查拒绝；标题压框、挂角徽章、标签、飘带等伸出边框的元素是推荐而非必需，写进版面 JSON 即可，编译提示词统一写“伸出边框的元素画在边框之上”。通道不支持透明输出时按不透明提交。透明要求只靠提示词里的“外轮廓以外留空、实心”与请求的透明底，不走透明规则分析。
- v4 不接受用户整段改写提示词（C 端不下发 `promptTemplate`，服务端返回“不支持自定义画面描述”）。提示词修复不得改写 v4 的提示词（可改写片段为空）。
- 编译后的提示词照常经提示词出口门禁送审。诊断 `promptCompilation.mode = design_spec_v1`，记录编译器版本、冻结语义哈希、档位、印花形态、附图方式与外形泄漏等检查提示。

## 单条模板字段分级

### 高保真生成必需

| 字段                    | 用途         | 要求                                                         |
| ----------------------- | ------------ | ------------------------------------------------------------ |
| `id` / `sourceIdentity` | 稳定身份     | 推荐；缺失时允许按唯一 key 兼容导入                          |
| `key`                   | 可读业务标识 | 可修改、可重复；小写字母开头，只含小写字母、数字、`-`        |
| `title`                 | 模板展示名称 | 1–80 字                                                      |
| `referenceImage`        | 模板参考图   | 本地文件或可长期读取的 HTTP(S) 地址                          |
| `promptTemplate`        | 基础画面内容 | 必须引用每个开放输入槽，并提供合理默认值                     |
| `inputSchema`           | 用户输入定义 | 固定 v2；模式正交；每个 id 唯一，只开放“画什么”              |
| `runtimeSemantics`      | 运行语义权威 | 必须与输入槽和目标实例通过交叉校验                           |
| `imageSize`             | 输出尺寸     | 使用平台支持的正典尺寸                                       |
| `status`                | 上线状态     | Agent 新产物固定为 `DRAFT`，由运营检查后决定直接上架或先试跑 |

`cover` 通常与 `referenceImage` 相同，但职责不同：`cover` 用于展示，`referenceImage` 会真正进入生图请求。即使 URL 相同也应分别写清，不能只给封面而漏参考图。

### 按需填写

| 字段                       | 何时需要                                                                                                                                                                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `backgroundPreference`     | 可选表单默认偏好：`inherit`（平台默认）、`transparent`（推荐透明）、`original`（推荐原版）；用户选择优先，不改变设计合同                                                                                                                              |
| `printPlacementPreference` | 可选商品预览与编辑器初始摆放偏好，默认 `inherit`；只影响印品预览落位，不参与生成。按设计形状选：小标/胸标类图案选 `front-left-chest` 或 `front-chest-center`；整幅海报/场景图选 `front-large-center`；专为背面设计的选 `back-*`；拿不准就留 `inherit` |
| `description`              | 给用户解释模板效果                                                                                                                                                                                                                                    |
| `imageN`                   | 需要覆盖默认单张输出时；通常保持 `1`                                                                                                                                                                                                                  |
| `kind`                     | 仅明确需要 `STYLE_REF` 或 `SKILL` 时；普通模板省略或写 `PROMPT`                                                                                                                                                                                       |
| `preprocessSteps`          | 必须先识图或做结构化文本变换时；没有就写 `[]`                                                                                                                                                                                                         |
| `metadata`                 | 保存 UI 建议、分类、标签、分析理由和优化审计                                                                                                                                                                                                          |
| `featureKeys`              | 模板专题挂载                                                                                                                                                                                                                                          |

### 运维往返字段

作者或 Agent 从零创作时，`featureKeys` 仍是可选的专题挂载建议，`makerKey` 也不应由作者凭空决定；
但从 Development / UAT / 生产模板中心下载的**作者模板 JSON**是运维往返文件，会保留库内已经确认的
`GalleryTemplate.id`、全部 `featureKeys`、`makerKey` 与来源身份。它可以原样回到“添加模板”做零写入
分析：内容和关系未变化时应判为“无变化”，不能因为可读 `key` 相同就猜测模板身份。

- `GalleryTemplate.id` 是站内模板身份；`key` 是可读业务标识，不是唯一身份。同 key 但新 ID 必须由
  运营明确选择覆盖、新建或本次跳过。
- `featureKeys` 表达模板所在的**专题策展集合**。回导时与目标环境已有关系及页面指定的默认专题取
  并集，只新增缺失关系，不移除、不重排目标环境已有选品。
- `makerKey` 表达这条模板依赖某个 Maker 的独立交互流程。Maker 依赖模板仍在模板中心维护；它不是
  可独立使用的图库模板，也不因此成为 Maker 配置或组件。

作者模板 JSON 支持 Development / UAT / 生产的本环境导出、修改与回导，不属于 `GalleryTemplatePromotion`
的可信发布载荷。生产可导出当前模板，保留 ID 修改后从“添加模板”完成零写入分析与确认，变更项录成草稿，
再独立执行上架检查。UAT → 生产是可选发布通道，只有选择该通道时才需要 UAT 发布文件及生产发布中心审查。

### Agent 不应决定

- `templateVersion`、`contentHash`。`id` 由工具生成，Agent 不自行编造语义化值。
- 自定义 `stageKey` 或 `remoteRunKind`，除非平台明确下发允许值。
- `sortOrder` 等目标环境运营状态；从零创作时也不要自行指定 `makerKey`。模板中心的运维导出会保留
  已确认的 `makerKey` 供无损回导。
- `promptEnhancement` 的第二份手写约束。
- `runtimePromptContext`、来源组、任务实例绑定、hash 和 claims；这些是每次运行时生成的任务数据。

```json
        "人物身份输入只接管各自人物身份；图片模式下，其来源图的原始背景、构图、色彩与光影不得进入环境目标",
        "环境输入接管两位人物轮廓外的完整环境；图片模式下，上传环境图是该目标唯一视觉内容来源，不从人物身份图或模板默认环境补取内容"
      ],
      "colorAndLight": ["仅在模板确实必须锁定色光时填写"]
    }
  },
  "metadata": {
    "tags": ["双人", "纪念插画"]
  }
}
```

## `runtimeSemantics` 如何保存制作人意图

### `targetInstances`：成图中有哪些可被接管的位置

每个实例必须回答：

- `id`：稳定技术标识，只用于引用。
- `kind`：`identity_subject` 表示一个固定身份人物/主体；`identity_group` 表示人数跟随一张合照、整体接管一个可伸缩区域的动态身份群组；`content_element` 表示不需要从用户图片保留身份的道具、模板固定宠物、装饰等内容。需要保留宠物身份时使用身份目标，不把它降级成普通内容。
- `role`：这个位置是什么，例如“中央大爱心中的男生主肖像”。
- `region`：它在哪里，例如“画面中央的大爱心容器内”。

`groupId` 当前可选且缺少确定性执行分支。普通 Agent 模板应省略；不能指望只填 `groupId` 就自动保持群体关系，真正必须保持的关系要写进 `visualContract.relations`。

只列出以下目标：

1. 会被用户输入替换的可见位置。
2. 必须明确声明“不能被上传身份接管”的关键内容位置。

不要把每一颗星星、每一片叶子都拆成目标实例。过细会扩大 JSON、任务快照和 LLM token，却不会提高保真度。

### `inputBindings`：哪个输入接管哪个目标

#### 内容值的用途：`valueKind`

`replace_content` 可显式声明 `valueKind`，表达标量输入应如何进入画面：

- `scene_description`：按描述绘制场景、环境或道具，不把整段描述当作需要写出的文案。
- `exact_text`：在目标位置逐字呈现输入文字，保留大小写和标点。
- 缺省：保持历史行为，按目标职责与位置描述中的关键词判断；不自动补写历史版本。

新写的内容绑定推荐明确声明。目标位置中的“文案之外”“标题旁边”只说明位置，不能决定
输入是文案；显式声明优先于这些词。声明只约束文字模式，上传图片仍按原内容图片绑定执行。
同一 binding 的全部目标共用该用途，需要混合用途时拆成各自输入绑定。身份 binding 不接受此字段。
上传作品配方由受控编译器明确区分背景/物体描述和观察到的文案，配方升级形成新版本。

#### 身份替换

单个身份目标使用：

```json
{
  "operation": "replace_identity",
  "targetIds": ["一个明确身份目标"],
  "bindingPolicy": "one_to_one",
  "renderingMode": "illustration_redraw",
  "allowedSourceGrouping": ["single_subject"],
  "groupToSinglePolicy": "reject"
}
```

模板中同一个人物需要固定重复出现两次或更多次时，必须把每个可见位置分别声明为 `targetInstances`，再使用：

```json
{
  "operation": "replace_identity",
  "targetIds": ["portrait_center", "portrait_top_left", "portrait_top_right"],
  "bindingPolicy": "same_source_repeated",
  "renderingMode": "illustration_redraw",
  "allowedSourceGrouping": ["single_subject"],
  "groupToSinglePolicy": "reject"
}
```

两种策略都只接收一张已确认的单主体图：

- `one_to_one` 必须且只能绑定一个身份目标。
- `same_source_repeated` 必须绑定至少两个互不重复的身份目标；同一上传人物的完整身份会逐一接管所有目标。
- `targetIds` 内不得重复。模板里每个应被替换的可见人物实例都必须列出，不能只声明“主人物”，再靠 `relations` 散文暗示其他脸也要替换。
- 目标位置只提供布局、姿势、表情、服装、遮挡与层级，不继续提供模板原人物身份。

#### 服装归属：`clothingOwnership`

上一条“目标位置只提供……服装”是默认行为，但不是唯一合法意图——运营常见的另一种要求是“身份图带来的衣着也要一起替换”。`replace_identity` binding 可以显式声明 `clothingOwnership: 'source' | 'template'`，把这条默认行为的例外落成结构化字段，取代此前只能在 `visualContract.relations` 里用特定中文措辞（如“服装随身份图替换”“服装保持模板设定”）表达服装冻结的旧做法：

- `'source'`：服装随身份图一起替换。上传图里穿什么，这个身份位置的成图就穿什么；目标位置原有的服装描述作废。
- `'template'`：服装锁定模板默认，与上一条默认行为一致——身份替换只接管人物身份，目标位置声明的服装、遮挡与层级继续沿用模板。
- 缺省：平台从 `visualContract.relations` 的散文措辞推断三态中的哪一种（现行为，不变）。**新模板推荐显式写该字段**——显式字段判定优先于散文正则，不会因为运营改写措辞、或散文命中别的判据而误判。

```json
{
  "operation": "replace_identity",
  "targetIds": ["一个明确身份目标"],
  "bindingPolicy": "one_to_one",
  "renderingMode": "illustration_redraw",
  "allowedSourceGrouping": ["single_subject"],
  "groupToSinglePolicy": "reject",
  "clothingOwnership": "source"
}
```

旧散文写法仍然兼容：已发布模板不要求回填这个字段，运行时按原有散文判据继续解析，只有新写的模板才要求显式声明。`clothingOwnership` 只出现在 `operation: "replace_identity"` 的 binding 上（`one_to_one`、`same_source_repeated`、动态群像的 `preserve_group` 均适用），`replace_content` 与 `reference_only` binding 不接受该字段。

这套边界与当前已完成的客户端能力一致：一个含图片模式的槽位上传一张单主体照片，在模板媒介中重新绘制到一个或多个作者预先声明的固定身份位置。`same_source_repeated` 不表示动态人数，也不从合照中选人。

这里的“可执行”只表示字段、任务快照、约束账本、提示词和图片角色都有确定性闭环，不承诺图像模型能在任意画风与任意实例数量下保持高人脸相似度。`same_source_repeated` 模板强烈建议至少用三组输入试跑；任一组出现“只复制发型、仍保留模板脸”或某个目标未替换，都应修正后再发布，但平台仍允许运营承担风险直接上架。普通固定位置多实例替换先使用当前无 mask 的短执行投影，不因一次失败就升级为 mask，也不能靠继续加长提示词碰运气；只有多组回归仍稳定漏掉特定局部目标时，才把可定位区域或显式 mask 作为后续能力升级。

#### 动态合照群组

`runtimeSemantics.version: 2/3` 支持一张合照整体驱动一个动态身份群组。它不是把合照预先拆成三人、四人或若干单人槽，而是把所有同类别成员绑定到一个可伸缩目标区域，由运行时读取合照可见事实并在最终提示词中明确人数与自动布局职责。

动态人物群组的目标写法：

```json
{
  "id": "family_group_region",
  "kind": "identity_group",
  "role": "围绕中央小狗的全部家人",
  "region": "中央小狗四周的可伸缩群像区域",
  "memberKind": "person",
  "minMembers": 1,
  "maxMembers": 12
}
```

对应 binding 固定为：

```json
{
  "operation": "replace_identity",
  "targetIds": ["family_group_region"],
  "bindingPolicy": "preserve_group",
  "renderingMode": "illustration_redraw",
  "allowedSourceGrouping": ["group_photo"],
  "groupToSinglePolicy": "reject"
}
```

作者与运行时共同遵守以下不变量：

- 输入槽只声明图片模式且固定 `maxCount: 1`，不同时声明文本模式；一张普通上传值会由作者 binding 消歧并冻结成 `group_photo`，客户端不需要另传隐藏字段。
- `preserve_group` 必须且只能指向一个 `identity_group`；反过来，`identity_group` 不能使用 `one_to_one` 或 `same_source_repeated`。
- `memberKind` 只允许 `person` 或 `pet`，`1 <= minMembers <= maxMembers <= 20`。它定义这个槽要识别和保留的成员类别，不是模板默认画面里画了几个人。
- 未提供结构化人数时，人数跟随合照中该类别的全部可见成员，由运行时视觉规划识别并写入执行提示词；不得沿用模板默认人数，也不得新增、复制或遗漏成员。若上游明确提供 `expectedSubjectCount` 或完整 `members`，运行时会校验上下界、成员 id 唯一性和两者数量一致性。
- `region` 必须描述可伸缩群像区域，`visualContract.composition` 写清人数变化时的自动排布骨架，`relations` 写清所有成员都必须参与的共同动作、接触、遮挡和层级。静态三人位、四人位不得冒充动态区域。
- 人物与宠物是不同成员类别。当前正式合同不从同一张人宠混合合照里静默拆出两个身份群组；需要同时保留人物和宠物身份时，使用“人物合照槽 + 宠物组合槽”两个输入和两个 `identity_group` 目标。
- 当前能力是单次图像规划 + 确定性 Prompt Compilation，不是像素级检测、逐成员裁切或结果后验验收。`minMembers / maxMembers` 对显式结构化人数是硬闸；普通上传的实际人数与共同关系无法靠静态校验确认，建议用三组试跑验证，未试跑时后台持续显示质量提醒。

以下能力仍不要让 Agent 声称已支持：

- `distinct_subjects` 多图自动分人。
- 从合照中选择某一个成员。
- 同一人物多参考图的普通客户端确认交互。
- 人宠混合合照自动拆成两个身份群组。
- `preserve_pixels`。

同一主体多参考图只有在客户端明确收集 `sourceGrouping=same_subject_multi_reference` 后才能使用；未完成该交互前也应保持关闭。

#### 内容替换

- 一个输入替换一个目标或一个整体装饰组：`replace_as_unit`。
- 一个输入明确描述多个固定目标，并要求保留这组位置：`preserve_target_group`。
- `match_declared_order` 当前没有完整的结构化顺序执行闭环，不用于普通 Agent 模板。

#### 仅作参考

`reference_only` 当前缺少独立的确定性图片角色和 adapter 行为。普通 Agent 模板不使用该分支；模板参考图直接写 `referenceImage`。

#### 当前可执行能力矩阵

代码权威位于 `src/modules/gallery/templates/executable-capabilities.ts`。导入校验、后台预分析、表单保存和发布必须共同消费该注册表，不能各自维护“看起来支持”的组合。

| 输入模式 | 运行操作           | 目标类型           | 可用呈现            | 预处理      | 生图执行                  |
| -------- | ------------------ | ------------------ | ------------------- | ----------- | ------------------------- |
| text     | `replace_identity` | `identity_subject` | 文本独立 / 文图复合 | 无          | 文本进入最终 prompt       |
| text     | `replace_content`  | `content_element`  | 文本独立 / 文图复合 | 无          | 文本进入最终 prompt       |
| image    | `replace_identity` | `identity_subject` | 图片独立 / 文图复合 | 无          | `identity_reference` 直通 |
| image    | `replace_identity` | `identity_group`   | 图片独立            | 无          | `identity_reference` 直通 |
| image    | `replace_content`  | `content_element`  | 图片独立 / 文图复合 | 无          | `content_reference` 直通  |
| image    | 无 binding         | 无                 | 仅图片独立          | vision-only | 提取结果进入最终 prompt   |

同一个图片槽不能既声明直接 replacement binding，又被 vision 步消费。worker 会把 vision 输入从直通图片集合中过滤；两种声明并存会造成“上传成功但生成时没有替换”的静默失败，因此校验器必须在导入或发布前要求二选一。vision-only 步的输出也必须被 `promptTemplate` 引用。

### `visualContract`：哪些视觉维度必须跨用户改写保留

- `medium`：必填，一句正向描述“是什么媒介”。例如“具有透色笔触的水彩婚礼涂鸦”。纸面载体、画布底色与媒介分开写；“水彩透色”不等于文件带 Alpha 透明通道。
- `styleTraits`：必填，列画风特征、头身比例、笔触、材质。
- `composition`：必填，列画幅、区域、大小层级、留白和阅读顺序。
- `relations`：必填，列接触、遮挡、怀抱、靠近、容器承载和身份不得扩散等关系。
- `colorAndLight`：可选，只有色光是模板不可替代卖点时才锁定。

不要把具体默认人物身份写进 visual contract。默认人物属于基础画面内容；用户上传身份应能替换它。也不要把用户可改的道具、地点或天气同时写成必须保留的约束。

### 适配原版与透明输出

模板作者描述设计内容；运行时根据用户选择决定是否透明输出。设计约束继续使用已有 `promptTemplate` 与 `visualContract`；可选 `backgroundPreference` 只决定新表单的默认选择，不把 `background`、缓存规则或用户预览底色塞进 `metadata`。原版的底色仍可写在基础画面中，不能为了支持透明版把所有模板改成永远无背景。存量模板继续按需分析透明规则，不要求批量回写数据。

**先按用途区分区域，再写约束。**

| 区域用途                                       | 作者应写清什么                                                 | 透明版本的处理                                       |
| ---------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| 只承载设计的画布、纸底、外围渐变与光晕         | 与笔触、字形和主体配色分别描述                                 | 移除载体，保留画风与前景                             |
| 局部设计元素，如徽章、文字底牌、报错窗口、包装 | 在 `relations` 写清承载关系，在 `styleTraits` 写清内部填充     | 保留已有局部轮廓与填充，不按“底板”一词删除           |
| 核心场景或可被内容槽接管的环境                 | 写清内容来源、必须保留的空间关系；存在局部边界时描述其实际范围 | 有明确边界才透明外围；不能删除环境目标或凭空新增相框 |

不要按前后位置判断去留。“标题在背景上方”只是位置描述，标题仍是前景设计内容；“人物后方的水族馆”可能是模板核心叙事。若核心环境占满画幅且没有可分离范围，应标为透明适配待确认，不能仅因输出文件有 Alpha 就宣称通过。原版仍可独立使用；该质量结论不新增模板上架硬门禁。

作者约束应保持原子化。例如，将“白纸底水彩，白字带描边，背后是蓝色报错窗口”拆为：

- `medium`：具有透色笔触的水彩插画。
- `promptTemplate`：默认基础画面采用白色纸底，保留原版视觉。
- `styleTraits`：标题采用白色实色字形与紧贴字形的描边。
- `relations`：报错窗口是独立设计元素，窗口内部的蓝色填充与内容共同保留。

这里只演示字段职责，不要求每个模板添加同样的文字或窗口。作者只写模板独有的约束，RGBA、预览底色隔离等通用交付要求由运行时统一提供。

**白色按用途处理，不按颜色统一删除。** 实色插画的白毛、白衣、字形、包装白底应保留；版画中代表纸张的留白、排线空隙才按油墨表达透明。只有模板确实采用油墨与纸白构图时才描述该语义，不能因为描线多就默认为单色或双色调。混合媒介应逐区域说明，不能让“去纸白”覆盖实色插画部分。

字形的实体笔画与字腔应分别判断：实心白字保留笔画填充，字母 O 的中心等原有字腔才透明，不能把实心字改成空心描边。局部场景内部的连续水彩色域也是设计内容，不能以“人物轮廓之外”为由再次挖空；透明边界位于该场景外围，颜料区保持原有连续性与透色。

**透明适配不改设计意图。** 人物身份、人数、动作、文案、服装归属、整体配色及残影的同身份关系保持原有合同。独立文字不新增连接字块的底板，已有文字底牌则按设计保留；双色调和随商品底色改字色属于另外的设计选择。模板约束不得固化某次上传图的身份特征，透明规则要能被下一张图片复用。

透明质量试跑在既有三组不同输入的基础上，分别检查原版与透明版，并切换白色、藏青、复古红、蓝、黄预览底板。检查内容与身份保持、局部白色填充、字形内孔、细线毛发、外围色晕和场景边界；场景边界未决时记录阻断原因，不强行算作成功。不使用透明像素比例代替视觉验收，也不把缓存命中等同于成图质量合格。运行范围与缓存升级方式见 [透明模板生成](./transparent-generation.md)。

## 三份作者信息如何分工

| 作者信息                    | 放在哪里                    | 是否进入 Prompt Compiler       |
| --------------------------- | --------------------------- | ------------------------------ |
| 基础画面里有什么            | `promptTemplate`            | 是，先解析成 `baselinePrompt`  |
| 用户能替换什么              | `inputSchema`               | 间接；本次激活值进入运行上下文 |
| 替换到哪里、必须保持什么    | `runtimeSemantics`          | 是，作为结构化合同             |
| UI 文案、候选示例、分类标签 | `metadata` 或 input UI 字段 | 否                             |
| 分析理由、优化轮次、审计    | `metadata`                  | 否                             |
| 旧增强层配置                | `promptEnhancement`         | v2 否，v1 兼容链是             |

核心规则：同一条成图意图只保留一个作者权威。基础内容归 `promptTemplate`，运行约束归 `runtimeSemantics`；不要再把 visual contract 手抄到 `promptEnhancement`。

## Agent 输出前的强制校验

每条模板必须满足：

1. `promptTemplate` 引用了每个开放输入槽。
2. 每个直通图片模式都有与目标类型匹配的 `replace_identity` 或 `replace_content` binding。
3. 每个 binding 的 input id 存在于 `inputSchema`。
4. 每个 `targetId` 存在于 `targetInstances`。
5. 身份输入只绑定 `identity_subject` 或 `identity_group`；内容输入只绑定 `content_element`。
6. 同一个身份目标不会被两个输入槽同时接管。
7. 固定身份模板只允许 `single_subject`；`one_to_one` 只绑定一个目标，`same_source_repeated` 绑定至少两个互不重复的固定目标。动态群像必须是 v2 的 `identity_group + preserve_group + group_photo`，且只绑定一个可伸缩群组目标。
8. `medium` 非空，且 visual contract 不包含具体默认人物/IP 身份。
9. 用户可替换的内容没有同时写进必须保持的 visual contract。
10. 同时含身份图与内容图时，目标 role 使用稳定职责而非默认题材，relations 已排除身份图背景串入内容目标，并在 `replace_as_unit` 时把激活的内容输入声明为该目标唯一视觉内容来源。
11. 作者 JSON 没有用固定“图一”“图二”表达来源身份；图片顺序和角色说明由运行时动态生成。
12. `metadata` 中的重要运行信息已经提升到 `promptTemplate` 或 `runtimeSemantics`。
13. 新模板固定 `DRAFT`，导入预分析无 error 后再试跑。
14. 若执行质量试跑，使用三组不同输入检查身份位置、构图、媒介和关系；同时含身份图与内容图时包含一组来源冲突明显的对抗输入。未完成时明确标记待试跑，不冒充已有证据。
15. 可能提供透明版本时，媒介与画布载体已分开，局部底牌、白色填充及核心环境的保留意图明确；没有用透明化改变绑定、人数、文案或自动切换双色调。无法确定核心场景边界时，明确记录透明适配待确认。

## 唯一推荐口径

给模板分析 Agent 的任务不是“写一段更完整的提示词”，而是输出三个互相引用的结构：

1. `inputSchema`：用户可以提供什么。
2. `targetInstances + inputBindings`：这些输入分别接管什么。
3. `visualContract`：无论用户怎么改，模板制作人的哪些视觉意图必须保持。

`promptTemplate` 负责把它们落成基础画面；MySQL 版本行负责冻结作者合同；任务 `runtimePromptContext` 负责冻结本次执行；Prompt Compiler 只负责编译，不负责从 metadata 或参考图重新猜合同。

## 契约维护

本文件使用稳定路径并原地迭代。作者字段或制作流程变化时：

1. 更新本文件中的步骤、字段归属和完成标准。
2. 同步更新 [`template-import/agent-v2-example.json`](./template-import/agent-v2-example.json)；传输结构变化时再更新 `schema.json`、导入 README 和代码 Schema。
3. 仍需服务存量数据的旧规则保留在对应 `LEGACY` 文档；旧文档首屏只描述它的兼容触发条件并指回本文。
4. 运行真实样例校验，并检查 `AGENTS.md` 与 `docs/README.md` 仍只有本文被标记为新模板作者合同的 `CURRENT` 正本。

完成标准：新模板 Agent 只从一个入口获得全部作者规则；兼容导入器的宽松行为不会被描述成新模板要求；所有公开样例均通过当前校验器。
