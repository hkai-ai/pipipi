# Agent 执行架构简化计划

本文面向产品负责人和实施者，记录 Agent 架构改造的范围、优先级、完成标准和推进方式，便于后续逐项落地。

记录日期：2026-11-02。状态：计划已记录，实施任务尚未开始。P0、P1、P2 表示本计划的执行优先级。

本计划管理待办与验收，不替代当前设计。现有行为以代码、测试及 [Process Runtime 设计](process-runtime-design.md)、[Agent Conversations 设计](agent-conversations-design.md) 为准；任务完成后同步更新对应设计文档。

## 本轮目标

先围绕两个真实场景整理架构，减少重复封装，让新增能力和阅读代码更直接。

| 场景 | 用户体验 | 本轮需要做到 |
| --- | --- | --- |
| 指定 Skill 执行 | 用户选择产品功能、提交内容，系统按确定的方法完成任务 | 服务端把功能绑定到固定版本的 Skill，复用执行、工具和结果校验能力 |
| 持续上下文对话 | 用户先讨论需求，再执行，之后接着调整或引用之前的结果 | 保留同一会话的上下文，支持普通交流和受控业务执行，能够恢复历史与资源引用 |

“指定 Skill”是服务端的执行选择。产品调用方仍提交业务身份和内容，不直接传 Skill、模型、Tool 或运行配置。

跨会话积累用户偏好、形成个人 Agent 的长期记忆留到后续阶段。同一会话的持续上下文与个人长期记忆分开建设。

## 架构方向与复用边界

优先整理现有模块，形成两条清晰的执行路径。模块职责独立不等于必须拆成独立服务。

| 部分 | 应承担的职责 | 优先处理方式 |
| --- | --- | --- |
| 产品入口与业务定义 | 确定用户请求的业务能力、输入输出和版本 | 保留 Business Process 与 Process Registration，减少重复配置和入口拼装 |
| 中心化 Skill 库 | 集中维护做事方法、版本和适用范围 | 复用现有固定版本与校验机制；当前仍可随应用发布本地快照，不先建设在线下载服务 |
| Agent Runtime | 加载本次获准的 Skill 和工具，驱动模型执行 | 优先复用 Pi 的会话、模型调用、工具循环、事件和取消能力；不重写同类循环 |
| Runtime Worker | 领取并执行任务，支持后续增加执行实例 | 复用现有任务领取、租约和恢复机制；先跑通两条路径，再按容量需要扩容 |
| 上下文管理 | 保存会话历史、已确认需求和资源关联，为本次执行准备上下文 | 复用现有会话持久化；与 Worker 职责分开，不因更换执行实例丢失会话 |
| 业务能力与工具 | 执行图片生成、内容处理、存储等实际操作 | 复用现有 Business Capability 和 Adapter；可共享管理，是否独立部署按真实需求决定 |
| Harness 运行约束 | 限制可用工具、时间、费用和副作用，验证业务结果 | 复用现有约束并整理归属；业务规则由项目拥有，不交给 Skill 文本自行保证 |

Pi 能复用哪些具体接口、哪些现有封装可以删除，在 P0-1 对照项目安装版本确认。不能因为上游有某个能力，就直接替换项目的持久化、身份隔离或业务幂等机制。

[DeepSeek Super Agent 与 Pi 调研](research/deepseek-super-agent-pi.md)作为方案参考。DSH 或 pi-durable 不预设为替换目标；只有明确解决当前问题、能减少现有实现且满足部署约束时，才提出采用方案。

## P0：形成最小公共执行结构，跑通两个场景

按编号顺序推进。P0 的目标是完成一组可用样板，保留未迁移业务的现有行为。

| 编号 | 任务 | 具体工作 | 完成标准 | 状态 |
| --- | --- | --- | --- | --- |
| P0-1 | 盘点现有实现，确定删改边界 | 跟踪指定 Skill 与持续对话的完整调用链；列出保留、合并、替换、删除的模块；核对可复用的 Pi 能力 | 有代码位置和原因支撑的改造清单，能说明重复在哪里、哪些业务差异必须保留 | 待开始，下一项 |
| P0-2 | 确定最小公共执行结构 | 明确 Skill 定义、Pi 执行、业务工具、上下文与运行约束的职责；用两个真实场景走通设计 | 两条执行路径清晰；不新增重复能力目录、第二套权威状态或重复执行循环 | 待开始 |
| P0-3 | 落地指定 Skill 执行 | 选择一个现有能力作为样板，串起固定 Skill、输入、执行与结果校验；复用 Pi 和已有业务工具 | 保持原有产品行为；同类新 Skill 无需复制整套 Agent 包装；同次删除样板中被替换的实现 | 待开始 |
| P0-4 | 落地持续对话 | 复用公共执行结构，恢复共享记录中的上下文；支持自然交流并接入样板能力 | 用户可讨论、选择、执行，再在下一轮引用结果；普通交流不强制调用业务工具 | 待开始 |
| P0-5 | 验收两条完整路径 | 检查产品接入、图片资源交接、用户隔离、执行预算、重复提交、超时和重启；核对部署所需配置与资源 | 两个场景端到端可用，关键保障保持有效；明确记录尚未验证的外部依赖，不以单元测试代替真实接入验收 | 待开始 |

样板在 P0-1 盘点后选择，不预先用最复杂的业务承担全部改造。未迁移部分列入 P1，明确去向，避免新旧实现长期并存。

P0 验收至少覆盖以下情形：

- 通过原有业务入口执行固定能力，仍获得符合原合同的结果。
- 同一会话先澄清需求，再执行任务，下一轮能引用先前结果和图片。
- Worker 重启后可恢复已保存的上下文；不把恢复误当成重新提交付费操作的许可。
- 不同用户不能访问彼此的会话与资源；取消和截止时间能传到实际执行。
- 新的执行结构确实减少重复包装，业务规则、版本约束与必要校验仍有明确归属。

## P1：迁移其他能力，降低日常维护成本

P0 验收后逐项推进；迁移按真实共性分批，不强迫所有业务共用相同的内部步骤。

| 编号 | 任务 | 具体工作 | 完成标准 | 状态 |
| --- | --- | --- | --- | --- |
| P1-1 | 分批迁移其他能力 | 按文本、图片、模板等实际差异分组；迁移可共享的执行部分，保留业务专属规则 | 每迁移一组就删除对应旧包装；原业务合同和版本保持有效 | 待开始 |
| P1-2 | 整理入口和配置 | 简化 HTTP 入口与启动组装；收拢同一能力的重复定义，修正职责错位 | 能从明确入口找到能力定义；修改业务规则不必修改通用 Worker | 待开始 |
| P1-3 | 完善长对话与使用反馈 | 根据 P0 暴露的问题改善历史整理、已确认需求、进度与取消反馈 | 对话变长后仍能保留关键需求；用户知道当前进度，取消确实停止可取消的工作 | 待开始 |
| P1-4 | 清理旧代码和说明 | 删除失效代码、只覆盖旧路径的测试和过期说明；更新架构与新增能力指引 | 读者能沿一条清晰路径理解和扩展系统，不需要同时理解两套同职能实现 | 待开始 |

P1-3 的基础取消、隔离与恢复保障已属于 P0；这一项完善体验和长对话质量，不用于推迟基础正确性。

## P2：出现实际需求后再启动

P2 是条件性工作，不要求 P1 完成后自动开工。

| 编号 | 任务 | 启动条件 | 优先复用与边界 | 状态 |
| --- | --- | --- | --- | --- |
| P2-1 | 多 Worker 部署 | 单实例出现可确认的并发或等待瓶颈 | 复用队列、领取、租约、恢复和过期执行隔离；同时核对部署及共享资源，不能只增加进程数 | 未触发 |
| P2-2 | Skill 独立发布与分发 | Skill 更新频率确实需要脱离应用发布 | 保留审查和不可变版本，采用受控分发；每次执行的 Skill 版本必须可确定 | 未触发 |
| P2-3 | 上下文或业务能力独立服务化 | 存在真实的跨产品复用、资源隔离或独立扩容需要 | 从已明确职责的模块拆出服务，继续复用现有合同和实现 | 未触发 |

本计划不包含个人长期记忆、专职多 Agent 协作或外部渠道自主接单。它们需要各自的产品场景和验收依据。

## 每一项如何执行

每次只推进一个明确工作项，并更新该项状态。一个工作项可以分多次修改，但不能借机扩大到其他阶段。

1. **明确边界。** 写清要解决的问题、涉及模块、复用内容和预计删除内容。以真实重复和职责问题为依据，不按文件大小决定删除业务规则。
2. **实施并替换。** 完成新路径时移除被取代的实现；必要的过渡路径记录用途和后续清理项。
3. **验证。** 代码变更遵循仓库默认检查：`npm run check`、`npm run typecheck`、`npm test`、`npm run build`。按变化补充有意义的合同或集成验证；联网、凭证、模型费用和外部写入的验收单独列出。
4. **交付。** 说明改了什么、删了什么、复用了什么、验证结果及剩余问题。同步对应设计、API 或业务文档，再进入下一项。

完成记录写在本文件中，详细设计与行为继续链接到各自的规范性文档，避免复制第二套说明。
